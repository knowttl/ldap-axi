# ldap-axi v1 design

This document defines the v1 command contracts and architectural constraints.
See the [support matrix](../support-matrix.md) for implemented commands, platform support, and qualification evidence.
The optional, in-repository `kerberos@7.0.0` source provider is the sole native-addon exception.
It exposes actual GSS confidentiality and integrity results and caller-supplied channel-binding application data through the sealed adapter.
GSSAPI traffic now negotiates the RFC 4752 security layer and frames post-bind LDAP PDUs through the protected stream.
§5.5 defines identifier resolution, §6.7 defines AD `groupType` decoding, and §14.1 defines the home view.

`ldap-axi` is an agent-facing CLI for reading LDAP directories from the shell, built to the AXI standard (the
[AXI standard](https://github.com/kunchenguid/axi)).
It targets Active Directory and generic LDAPv3 as equal first-class citizens, and it runs on Linux and
Windows.

Every factual claim in this document is traceable to a source in §21, read on 2026-07-31.
Claims marked **verified locally** were proved by running code on the development machine during this design
task, and the exact observation is quoted where it appears.
Where a claim could not be verified, it is written as an open question in §20 rather than stated as fact.

## 0. Invariant R: v1 is read-only

**ldap-axi v1 is read-only.
It requires only directory read access, and it implements no add, modify, modifyDN, rename, move, delete,
password-set, password-reset, or write-capable extended operation.**

This is a first-class architectural invariant, not a default posture and not a v1 convenience.
It is binding throughout v1; no flag, configuration, or extension may relax it.

Invariant R is load-bearing in six places, and each states it in its own terms rather than deferring to this
one:

| Where | What it says |
| --- | --- |
| §1.5 | The excluded capability classes, named as command-surface non-goals |
| §2.2 | Every registered operation carries a semantic read classification with its citation |
| §3 | Read-only is semantic, not operation-name-based, and the sealed client is the enforcement point |
| §4 | The mutation surface that exists in the protocol and is deliberately absent here |
| §11.7 | Operator provisioning asks for read access only, and what happens if the bind account is broader |
| §19 | Live tests use read-only credentials and may never issue a mutating operation |

**Read-only is semantic, not syntactic.**
The operation name is not proof of safety in either direction, and LDAP makes this sharper than any sibling
project in the fleet:

- **Extended operation is a single protocol operation whose safety depends entirely on an OID.**
  RFC 4511 §4.12 defines one `ExtendedRequest`.
  Through it, `1.3.6.1.4.1.1466.20037` is StartTLS and changes nothing, while `1.3.6.1.4.1.4203.1.11.1` is
  RFC 3062 Password Modify and changes a credential.
  A syntactic allowlist of operation *types* that admitted "Extended" would admit both.
  So §3.4 admits extended operations by OID, never by operation type.
- **Bind changes no directory entry and still has server-side effects.**
  A failed simple bind against Active Directory increments `badPwdCount` and can lock the account out.
  Bind is unavoidable, because an authenticated read requires it, so §2.3 admits it as a separately sealed
  authentication path and §11.6 forbids the credential-probing shapes that would turn it into a lockout
  weapon.
- **Compare returns a non-zero result code on success.**
  RFC 4511 §4.10 returns `compareFalse` (5) or `compareTrue` (6); neither is a failure and neither mutates.
  A client that treats "result code is not 0" as an error is wrong about Compare, and §12.5 states the rule.
  v1 registers no Compare operation (§2.1), but the classification is recorded because the naive read of the
  result-code table is what a future contributor would repeat.
- **A control can carry semantics its operation does not.**
  Controls ride along on an operation and change its behavior, so an allowlisted Search plus an arbitrary
  caller-supplied control is not a bounded read.
  §3.5 closes the control list for that reason.

So the boundary is neither the operation name nor the result code.
**For the CLI, plugins, documented exports, and supported package-specifier imports, the boundary is the operation registry in §2.1, the extended-operation OID allowlist in §3.4, and the control allowlist in §3.5, all enforced in the sealed client of §3.3.**
A hostile same-user process that locates and imports private installed files by absolute path, or directly loads the native addon, is outside this threat model.
Preventing that access requires process or operating-system isolation and is not a security property claimed by ldap-axi.

## 1. Scope and command surface for v1

### 1.1 The shape of the reference surface

`trxo/ldap-mcp` is a reference for what an LDAP tool surface typically exposes.
It is a **behavioral, domain, and scope reference only**: never a dependency, never a vendored copy, never a
fork base.
It is a Go MCP server (module requires Go 1.24+, `github.com/go-ldap/ldap/v3`, `github.com/mark3labs/mcp-go`),
speaking SSE over HTTP on `:8080` by default, in roughly 800 lines across four files, and its README states it
ships with no unit tests.

Its whole tool surface is five tools and two resources:

| Tool | Effect | Parameters |
| --- | --- | --- |
| `search_entries` | read | `base_dn`, `filter`, `scope` (`base`/`one`/`sub`, default `sub`), `attributes`, `size_limit`, `types_only`, `page_size`, `deref_aliases` |
| `get_entry` | read | `dn`, `attributes` |
| `add_entry` | **write** | `dn`, `attributes` |
| `modify_entry` | **write** | `dn`, `changes` |
| `delete_entry` | **write** | `dn` |

Its write tools register only when `-read-write` is passed, so its default posture is read-only by omission.
Resources are `ldap://root-dse` and `ldap://entry/{dn}`.

That surface is a generic LDAPv3 CRUD bridge, and reading it decided as much by contrast as by imitation.
What ldap-axi **borrows** is the parameter vocabulary that LDAP itself dictates: base, filter, scope,
attributes, size limit, page size, and alias dereferencing.
What ldap-axi **deliberately diverges from** is listed here, because each divergence is a design decision and
not an accident:

| Reference behavior | ldap-axi v1 | Why |
| --- | --- | --- |
| Read-only by *omission* of a `-read-write` flag | Read-only by architecture, with no flag that can open it | A flag that exists can be set; Invariant R is binding (§0, §3.3) |
| Output is a prose message plus a fenced JSON block in MCP text | TOON on stdout, one envelope | AXI §1 and §6; a fenced block inside a message is not machine-addressable output |
| Attribute values are all Go `string`, so `objectSid` and `objectGUID` arrive as raw bytes in a string | Binary attributes are decoded to their canonical string form and also offered raw as base64 | §6.2; a raw SID in a JSON string is unusable and can be invalid UTF-8 |
| No Active Directory handling at all | AD is a first-class flavor with decoding, nested groups, and sub-error translation | v1 requirement; §5, §6 |
| `page_size` drains every page server-side into one merged result | Always paged, one page at a time, with an explicit partial marker | §9.2, §9.3; draining is unbounded memory and hides truncation |
| Paging cookies are internal to the supported client API | Paging is in-process only, with bounded output and an explicit incomplete state | §9.3, §9.4 |
| Time limit hardcoded to 0, so only a socket deadline exists | Server-side `timeLimit` is set alongside the client deadline | §9.5 |
| Errors are the raw `go-ldap` error string, with `ErrNotFound` flattened to one message | Structured codes, translated, with AD sub-error extraction | §12 |
| `-bind-password` accepted on argv | No secret is ever an argument, enforced by a flag-registration guard | §11.2 |
| `-insecure` silently disables verification | `--tls-no-verify` is per-invocation only, warns on stderr, and reports `tls_verified: false` in the data | §10.5 |
| No base DN default and no rootDSE discovery | Base DN is resolved from the rootDSE per flavor, and ambiguity is an error rather than a guess | §5.3 |

### 1.2 v1 defines four read nouns and supporting commands

v1 buys depth in the reads that an agent actually chains when answering a directory question, and declines
everything else.

| Noun | Purpose | Flavor |
| --- | --- | --- |
| `entry` | `search` and `show`: the general LDAP read, with explicit base, filter, scope, and attributes | Neutral |
| `user` | `list`, `show`, and `groups`: user objects with decoded account state | Flavor-specific (§5.4) |
| `group` | `list`, `show`, and `members`: group objects and membership, including nested on AD | Flavor-specific (§5.4) |
| `computer` | `list` and `show`: machine accounts | AD-first, with a stated generic fallback (§5.4) |

Supporting commands add diagnostics, configuration discovery, and opt-in integration without adding a directory domain:

| Command | Purpose |
| --- | --- |
| `profile list`, `config path` | Offline configuration discovery (§17.1) |
| `server` | Print the rootDSE facts that matter: detected flavor, naming contexts, supported controls and extensions, and the server's own limits (§5.1). This is flavor detection made visible rather than hidden. |
| `auth status` | Report whether a credential resolved and from where, the recorded native provider status, the selected mechanism, the SASL security layer, the TLS channel binding, whether the channel is encrypted and verified, and the bound identity when the server supports RFC 4532 Who Am I (§11). `--offline` reports the same selection without contacting the directory, so a misconfiguration is diagnosable before any bind. |
| `setup` | Install the session hook and skill (§17) by explicit opt-in, per AXI §7 |

`entry` earns its place despite `user`, `group`, and `computer` covering the common cases: LDAP schemas are
open-ended, every real directory carries objects the four nouns do not model, and a directory CLI that cannot
express an arbitrary filter against an arbitrary base is not a directory CLI.
`entry search` is the escape hatch that keeps the typed nouns from becoming a cage, and it is exactly the
surface the reference exposes.

### 1.3 Deferred, with the reason

Deferring is a decision, so each carries its reason.
None of these is deferred *because* of Invariant R; the classes Invariant R excludes are in §1.5.

- **Schema browsing** (`subschemaSubentry`, object class and attribute type definitions).
  High value for an agent that must construct a filter against an unfamiliar directory, and genuinely large:
  parsing RFC 4512 schema definitions is its own subsystem.
  It should land once the four nouns are proven.
- **Security descriptor reads** (`nTSecurityDescriptor`, ACL inspection).
  This is a read, and permitted by Invariant R, but decoding a Windows security descriptor correctly is a
  substantial binary-parsing project and getting it subtly wrong would produce confidently wrong security
  answers.
  It is deferred on the grounds that a wrong ACL report is worse than no ACL report.
- **Password policy reads** (`msDS-PasswordSettings`, fine-grained policy resolution, computed effective
  policy).
  Requires resolving a policy precedence chain, which is inference layered on reads rather than a read.
- **Global Catalog search** (ports 3268 and 3269).
  A worthwhile forest-wide read, but it changes the base DN resolution model in §5.3, since the GC holds a
  partial attribute set across every domain in the forest.
  Deferred to keep v1's base resolution one rule rather than two.
- **DirSync, persistent search, and change notification.**
  `ldapts` ships `PersistentSearchControl` and `EntryChangeNotificationControl`, so the mechanism is
  available, but a change feed is a long-lived streaming session and v1's process model is one bounded
  invocation.
  Also, some change-tracking controls consume server-side state, which §3.5 must reason about individually
  rather than admit as a class.
- **Virtual List View and server-side sort.**
  `ldapts` ships `ServerSideSortingRequestControl` (OID `1.2.840.113556.1.4.473`, verified locally) but ships
  no VLV control, so VLV would be hand-rolled on the generic `Control` base.
  Sorting is deferred with it, because a sorted page and a paged sort interact (RFC 2696 paging plus sorting
  is not universally supported) and the honest answer needs a real directory to test against.
- **Live SASL GSSAPI and Kerberos single sign-on.**
  The provider foundation supplies the patched optional provider and retains the existing sealed binary bind path, but offline checks cannot prove ticket acquisition or server interoperability.
  Live qualification remains outside `npm run verify` and is bounded by §19.
  Until live qualification lands, operators that require a verified production path should use `--auth simple` explicitly.

### 1.4 Naming and grouping

Nouns are singular and each takes subcommands: `ldap-axi user list`, `ldap-axi user show <id>`.
This matches `azure-axi` (`resource list` / `resource show`), `awx-axi` (`job list` / `job show`), and
`falcon-axi` (`detection list` / `detection show`), so an agent that has used one AXI tool in the fleet
already knows the shape.

Where LDAP vocabulary and AD vocabulary disagree, the design picks the protocol term for the command and
reports the server's term in the data.
The clearest case is the noun `computer`: that is AD's object class, generic LDAPv3 has no equivalent standard
class, and §5.4 states what the command does on a directory that has no machine accounts rather than
pretending the noun is universal.

Every verb in the CLI is a read verb.
There is no `add`, `create`, `modify`, `set`, `delete`, `remove`, `rename`, `move`, `disable`, `enable`,
`unlock`, or `reset` verb anywhere in the surface, and §3.3 makes that structural rather than stylistic.

### 1.5 Command-surface non-goals

Named explicitly, because Invariant R is a promise about what the tool cannot do, and a promise stated only as
an architecture note is easy to erode:

- **No entry creation.** No `add`, no `create`, no import, no LDIF apply.
- **No attribute modification.** No `modify`, no `set`, no `append`, no `--set-attribute`.
- **No deletion.** No `delete`, no `remove`, no tree delete.
- **No rename or move.** No `rename`, no `move`, no ModifyDN in any form.
- **No password operation.** No set, reset, change, unlock, or expire.
  RFC 3062 Password Modify is denied by OID in §3.4, and the AD alternative of writing `unicodePwd` is a
  Modify and therefore already impossible.
- **No account state change.** No enable, disable, or `userAccountControl` write.
  v1 *reports* account state as data (§6.1) and that is exactly where a future contributor would look for a
  way to set it, so the help text on those fields says it cannot.
- **No group membership change.** No add-member, no remove-member.
- **No write-capable extended operation.** §3.4's allowlist has two entries and neither writes.
- **No LDIF export written to disk by ldap-axi.** Output goes to stdout, and the operator's shell owns
  redirection; there is no `--output-file`, so there is no path where ldap-axi creates a file of directory
  contents.
- **No credential probing.** §11.6.
- **No write-path test suite, gated or otherwise.** §19.

`awx-axi` reached the conclusion that a write suite should be deleted rather than gated, because a future contributor can enable a gate.
ldap-axi inherits the reasoning and does not need the gate: there is no write path to test, so there is no
write suite to delete.

### 1.6 The post-v1 extension path, marked unimplemented

Any future write-capable design must be separate from v1; it cannot arrive by relaxing a flag.
It arrives by widening the `effect` union in §3.3, which does not compile today, and that diff necessarily
touches the sealed client, the registry, the registry-integrity test, and this document in one reviewable
change.
That is the intended cost.

## 2. Protocol operations v1 speaks

### 2.1 The complete v1 operation registry

Five operations, closed.

| Operation id | LDAP operation | RFC 4511 § | Effect | Used by |
| --- | --- | --- | --- | --- |
| `rootDSE` | Search, base scope, empty base DN, `(objectClass=*)` | §4.5, RFC 4512 §5.1 | read | Flavor detection (§5.1), `server`, `auth status` |
| `searchPaged` | Search, with the RFC 2696 paged results control | §4.5 | read | Every data command (§9.2) |
| `bind` | Bind, simple, or the approved GSSAPI/SSPI SASL exchange | RFC 4511 §4.2, RFC 4513 §5.2, RFC 4752 | authentication, sealed separately (§2.3) | Every authenticated invocation |
| `unbind` | Unbind | §4.3 | read (teardown) | Every invocation, on exit |
| `startTLS` | Extended, OID `1.3.6.1.4.1.1466.20037` | §4.14 | read (transport upgrade) | `--start-tls` (§10.1) |

One further operation is admitted only through the §3.4 allowlist and is not a command surface:
`whoami`, the RFC 4532 Who Am I extended operation, OID `1.3.6.1.4.1.4203.1.11.3`, used by `auth status` when
the server advertises it in `supportedExtension`.

A multi-stage SASL bind can send more than one BindRequest with the same mechanism after `saslBindInProgress`.
Those messages are one logical authentication exchange, not retries.
The selected mechanism is immutable for the exchange.

Operations deliberately **not** registered, each for a stated reason:

- **Search without the paged control.** Not a separate registry entry, because §9.2 makes paging
  unconditional. This is the single most consequential omission in the registry and §9.1 is why.
- **Compare.** Semantically a read (§0) and safe, but no v1 command needs it, and the registry is closed to
  operations that are used, not to operations that are permitted. Registering an unused read would weaken the
  claim that the registry describes the actual traffic.
- **Abandon.** No directory change, but `ldapts` exposes no public `abandon` method (verified locally: the
  `Client` prototype carries no `abandon`), and v1's bounded invocations have nothing to abandon.
- **Add, Modify, ModifyDN, Delete.** Invariant R (§4).
- **Every extended operation except the two allowlisted OIDs.** §3.4.

### 2.2 The admission rule

An operation may enter the registry only with a **semantic read classification carrying its citation**: the
RFC section that defines the operation, plus an explicit statement of what state it changes, if any.
"It is named Search" is not an argument, and "it is not named Delete" is not an argument.

This is the LDAP form of the sibling evidence rules: `falcon-axi` requires two citations proving an endpoint's
scope is a read permission, and `awx-axi` keys on the HTTP verb at its transport seam.
Neither transfers directly, because LDAP has no scope strings and no HTTP verbs.
What transfers is the shape: the evidence is a required field on the registry entry, and a test in the local
required-check set fails verification if any entry has an empty citation or a classification other than the
permitted set.

The classification field is not free text.
It is one of `read`, `authentication`, or `transport`, and the type system permits no fourth value (§3.3).
`authentication` and `transport` exist because Bind and StartTLS are honestly neither pure reads nor writes,
and collapsing them into `read` would be the kind of small lie that makes the whole invariant unfalsifiable.

### 2.3 Bind is one selected authentication exchange

An authenticated read requires a Bind, but Bind is not a read, and the difference is operationally real:

- A failed simple bind against Active Directory increments `badPwdCount` on the target account and can trip the domain lockout policy.
- An ambient GSSAPI exchange avoids submitting an LDAP password, but still changes connection authorization state and produces authentication audit traffic.
- Bind changes the connection's authorization state, which is server state even though it is not directory state.

ldap-axi selects exactly one of anonymous, simple, or GSSAPI before sending any LDAP BindRequest.
`auto` attempts ambient GSSAPI/SSPI preparation and never selects the configured password implicitly.
Provider absence, no ambient credential, an expired ambient credential, and any KDC, SPN, runtime, policy, TLS, or server-side bind failure are terminal.
Simple authentication is selected only by explicit `--auth simple` or its non-secret configuration equivalent.

One invocation performs at most one logical authentication exchange.
A SASL exchange may contain bounded continuation BindRequest messages with the same mechanism as required by RFC 4513 §5.2.1.2.
It never changes mechanism, principal, service target, or credential source during that exchange.

`ldapts`'s `autoRebind` remains disabled.
A dropped authenticated connection is an error, not a reconnect and bind replay.
No credential-probing surface exists.

Bind is sealed on its own path in §3.3, because authentication is not one of the reads and must not travel the read path.

## 3. Read-only posture and client enforcement

### 3.1 What read-only means here, precisely

**v1 issues no protocol operation that changes any directory entry, and no extended operation outside a
two-OID allowlist that changes nothing.**

The naive formulations all fail for LDAP:

- "Search only" fails because Bind, Unbind, and StartTLS are all required and none is a Search.
- "Allow Search and Compare, deny the rest" fails because it denies StartTLS and therefore denies encryption.
- "Allow Search, Compare, Bind, Unbind, Abandon, StartTLS, and Extended" fails because Extended is the one
  operation whose safety is entirely an OID (§0), and admitting it as a type admits RFC 3062 Password Modify.
- "Deny the client methods whose names look mutating" fails for a fourth reason, specific to the chosen
  library and verified locally: `ldapts`'s `startTLS()` is implemented by calling its own `exop()`
  (`src/Client.ts` line 281, `await this.exop('1.3.6.1.4.1.1466.20037', undefined, controls)`), so a blanket
  ban on `exop` breaks encryption.

So the enforcement is three closed lists rather than one: registered operations (§2.1), allowlisted extended
OIDs (§3.4), and allowlisted controls (§3.5).

### 3.2 Where the boundary sits, stated as rules

- No operation that changes a directory entry is registered, and no code path can construct one.
- No extended operation OID outside §3.4's allowlist is issuable, and the allowlist contains only StartTLS and
  Who Am I.
- No caller-supplied control reaches the wire; the control set is internal and closed (§3.5).
- The `ldapts` `Client` instance never escapes the sealed module, because its mutating methods are reachable
  on it (§3.3).
- `src/directory/gssapi.ts` is the only permitted owner of the native provider seam.
  The adapter keeps provider objects and token callbacks inside the directory boundary, while the sealed client owns the raw LDAP sender and socket.
- Ordinary commands write no local state.
  The only planned local writes are the user-owned config file (§17) and the explicit `ldap-axi setup`
  installation of hook, plugin, and skill files.
  There is no credential file written by ldap-axi, no session or connection cache, no fixture recorder, no
  query result cache, and no output file (§1.5).
- The registry is closed: adding an operation requires its §2.2 citation in the same change.

### 3.3 The sealed client is the enforcement point

Safety does not depend on command-layer discipline.
One module owns the directory connection, and it is the only module in the tree permitted to import `ldapts`
or any Node network API.

```ts
type OperationId = "rootDSE" | "searchPaged" | "bind" | "unbind" | "startTLS" | "whoami";

type Effect = "read" | "authentication" | "transport";

type LdapOperation = Readonly<{
  id: OperationId;
  effect: Effect;
  evidence: Readonly<{ rfc: string; section: string; changes: string }>;
}>;

const OPERATIONS: Readonly<Record<OperationId, LdapOperation>>;

// The only exported surface. No Client, no socket, no raw send.
export interface Directory {
  readonly flavor: ServerFlavor;                                  // §5
  rootDSE(): Promise<RootDse>;                                    // §5.1
  searchPages(request: SearchRequest): AsyncIterable<SearchPage>;  // §9.2
  whoami(): Promise<string | undefined>;                          // allowlisted OID, §3.4
}

export function openDirectory(options: ConnectOptions): Promise<Directory>;
```

`openDirectory` performs connect, optional StartTLS, and Bind, then hands back a `Directory` whose surface is
three reads.
The package-root `openDirectory` export is the only supported production capability entry.
The package `exports` map rejects package-specifier deep imports, and no supported export carries a `Client`, socket, connection, raw request, filter string sink, low-level sender, or setter that could install one.
Private installed implementation files remain ordinary same-user files under the explicit threat-model limit in §0.

The provider seam is equally sealed within the supported production surface: only `src/directory/gssapi.ts` may dynamically import the package-relative
vendored provider entry point, and it may return only an opaque prepared exchange to the client boundary.
The binary SASL sender and socket-gating transport are internal to `src/directory/client.ts`.
Native/provider objects, raw LDAP senders, sockets, token callbacks, and tokens never escape through `Directory`
or command modules.

Six properties make this enforcement rather than convention:

1. **The `ldapts` `Client` is held in a module-private field and never returned.**
   This is stated as a property because the alternatives do not work, and the reason is verified rather than
   assumed.
   Verified locally on `ldapts@9.0.0`, the `Client` prototype's own property names are:
   `_connect`, `_destroySocket`, `_ensureConnected`, `_handleSendResponse`, `_nextMessageId`, `_onBindSuccess`,
   `_onConnect`, `_send`, `_sendBind`, `_sendSearch`, `add`, `bind`, `bindSASL`, `compare`, `del`, `exop`,
   `isBound`, `isConnected`, `modify`, `modifyDN`, `search`, `searchPaginated`, `startTLS`, `unbind`.
   Five of those mutate (`add`, `modify`, `modifyDN`, `del`, `exop`), and `_send` is a **runtime-reachable
   prototype property** despite being TypeScript-`private`, because TypeScript `private` is erased at
   compile time.
   So handing a `Client` to a command module, or wrapping it in a `Proxy` that forwards unknown properties,
   would leave `add`, `modify`, `modifyDN`, `del`, `exop`, and `_send` all reachable.
   The wrapper is therefore a distinct object that forwards a fixed set of calls, and the underlying instance
   is unreachable from outside the module.
2. **`effect` is a three-member union and none of its members is a write.**
   Writing `effect: "write"` does not compile.
   Widening that union is a deliberate, reviewable diff in the sealed module, which is exactly where §1.6 says
   such a change would have to be argued.
3. **Descriptors are frozen and verified at initialization.**
   Registry construction copies every input, recursively freezes each descriptor, its `evidence` object, and
   the outer record before any reference escapes, and verifies that each key is an own key of the registry and
   that the resolved descriptor's `id` matches its key.
   A retained mutable alias cannot relabel a canonical descriptor after initialization.
4. **Evidence is mandatory and machine-checked.**
   A test in the local required-check set walks `OPERATIONS` and fails verification if any entry has an empty
   `rfc`, `section`, or `changes` field, or an `effect` outside the union.
   That is the mechanical form of §2.2, and it is what stops an operation being added on assertion.
5. **A registry-integrity test asserts the whole surface.**
   One test asserts that `OPERATIONS` contains exactly the six ids in §2.1 plus `whoami`; that the runtime keys
   equal the `OperationId` set; that each effect and evidence value equals its canonical expected value; that
   the extended-OID allowlist is exactly the two OIDs in §3.4; and that the control allowlist is exactly the
   set in §3.5.
   The same test attempts to mutate every descriptor and nested value and asserts nothing changes.
   Changing the surface requires changing the union, the registry, and the test in one commit, on purpose.
6. **Exactly one module may import `ldapts` or a network API.**
   `src/directory/client.ts` is the sole file permitted to import `ldapts`, `node:net`, `node:tls`, or
   `node:dns`, enforced by a lint boundary rule and by an independent architecture test that scans the source
   tree and import graph.
   Process and shell execution are forbidden in runtime source because §15.1 forbids shelling out to `ldapsearch` or any platform binary.
   The native package install and target-native prebuild scripts are the only `node:child_process` exception, and they may invoke only the pinned `node-gyp` build tool.

### 3.4 The extended-operation OID allowlist

Extended operations are denied by default and admitted by OID.

| OID | Operation | Spec | Changes | Why admitted |
| --- | --- | --- | --- | --- |
| `1.3.6.1.4.1.1466.20037` | StartTLS | RFC 4511 §4.14, RFC 4513 | Nothing in the directory; upgrades the transport | Encryption on port 389 is otherwise impossible (§10.1) |
| `1.3.6.1.4.1.4203.1.11.3` | Who Am I | RFC 4532 | Nothing; reports the current authorization identity | `auth status` answers "who am I bound as" without a search (§11) |

Explicitly denied, and named so the denial is testable rather than implicit:

| OID | Operation | Why denied |
| --- | --- | --- |
| `1.3.6.1.4.1.4203.1.11.1` | RFC 3062 Password Modify | A write, and the exact operation Invariant R exists to exclude |
| `1.3.6.1.1.8` | RFC 3909 Cancel | Control-plane only and not a directory write, but v1 has nothing to cancel (§2.1) |
| everything else | any | Deny by default |

The allowlist is a frozen set inside the sealed module, checked before the extended request is issued.
The denial message names the attempted OID, so a bug report is one line long.

Two implementation notes that make this concrete rather than aspirational:

- The wrapper never exposes an extended-operation entry point to callers at all.
  `Directory` has no `exop`; `startTLS` happens inside `openDirectory`, and `whoami` is a named method whose
  OID is a module constant.
  The allowlist is therefore a second line of defence behind the absence of a caller-reachable path, not the
  only one.
- Because `ldapts.startTLS()` internally calls `exop` (§3.1), the allowlist must be consulted at the point
  ldap-axi decides to upgrade, not by monkey-patching the library's `exop`.
  Patching a library's internals to enforce a policy is a fragile pattern that breaks silently on upgrade, so
  it is not used.

GSSAPI Bind adds no extended-operation OID and no LDAP control.
The extended-operation allowlist and control allowlist remain unchanged.

### 3.5 The control allowlist

Controls modify an operation's behavior, so an unbounded control list makes a bounded operation list
meaningless.
v1 sends exactly one control, and accepts none from the caller.

| Control | OID | Why |
| --- | --- | --- |
| Simple Paged Results | `1.2.840.113556.1.4.319` | RFC 2696 paging, mandatory per §9.2 |

Three facts shape this section, all verified locally against `ldapts@9.0.0`:

- `PagedResultsControl` is present and its OID is `1.2.840.113556.1.4.319`.
- `ServerSideSortingRequestControl` is present, OID `1.2.840.113556.1.4.473`, and is **not** used in v1 (§1.3).
- The generic `Control` base accepts an arbitrary OID (`new Control("1.2.840.113556.1.4.1338").type` returns
  that OID), so nothing in the library prevents an arbitrary control being constructed.
  That is exactly why the allowlist lives in ldap-axi's sealed module rather than being assumed from the
  library's exports.

There is also a library constraint that makes the closed list the only workable design: `ldapts` attaches its
own paging control inside `searchPaginated`, and passing a `PagedResultsControl` explicitly throws
`Error("Should not specify PagedResultsControl")`.
So a caller-supplied control list could not have included the one control v1 actually needs.
There is no `--control` flag in v1, and adding one would be a change to this section.

### 3.6 Read-only is not the same as invisible

An authenticated read still touches the directory.
Every authenticated ldap-axi invocation performs a Bind, which AD logs and which affects `badPwdCount` on
failure (§2.3).
A large `entry search` consumes server-side resources and can hit `MaxQueryDuration` or `MaxTempTableSize`
(§9.5).
Directory servers commonly audit-log searches.

This is stated because "read-only" means no mutation, not no footprint, and an operator deciding whether to
point ldap-axi at a production domain controller deserves the accurate version.

## 4. The mutation surface, and why it is absent

§1.5 lists the excluded classes.
This section records the three cases where exclusion needed an argument rather than being obvious, so a future
reader does not mistake them for oversights.

**Password Modify is excluded even though it is the one write an operator most often wants from a directory
CLI.**
RFC 3062's extended operation is the standard way, `unicodePwd` Modify is AD's way, and both are writes.
More than that, a password write is the highest-consequence operation in a directory: it is irreversible from
the tool's perspective, it can lock a human out of everything, and it is the single most attractive target for
an agent that has misunderstood its instructions.
It is denied by OID (§3.4) and by the absence of Modify.

**Account unlock and enable are excluded even though they read like remediation rather than mutation.**
"Unlock this account" is a `lockoutTime` Modify and "enable this account" is a `userAccountControl` Modify.
They are excluded, and they get their own mention because v1 *reports* both states (§6.1) and a reporting
surface is where a future contributor will look for the matching action.
The help text on those fields says v1 cannot change them.

**Compare is excluded despite being a read.**
This is the mirror image of the other two: it would be permitted, and it still is not registered, because §2.1
keeps the registry to operations v1 actually issues.
Recording this prevents the registry being read as "everything safe" rather than "everything used".

## 5. Server flavor detection and per-flavor behavior

### 5.1 The rootDSE probe

Flavor detection is one operation: a base-scope Search with an empty base DN and filter `(objectClass=*)`
(RFC 4512 §5.1), requesting attributes **by name**.
Operational attributes are not returned by `*`, so the attribute list is explicit:

```
supportedCapabilities  supportedControl  supportedExtension  supportedLDAPVersion
supportedSASLMechanisms  namingContexts  vendorName  vendorVersion  subschemaSubentry
```

When the AD test in §5.2 passes, a second read collects the AD-only attributes:

```
defaultNamingContext  rootDomainNamingContext  configurationNamingContext  schemaNamingContext
dnsHostName  serverName  domainFunctionality  forestFunctionality  domainControllerFunctionality
isGlobalCatalogReady  supportedLDAPPolicies  currentTime
```

One rootDSE read per invocation, cached in memory for the life of the process.
It happens before any data command runs, because base DN resolution (§5.3) and per-flavor behavior (§5.4)
both depend on it.

That is a real, if small, cost: every data command pays one extra round trip.
It is accepted because the alternative is guessing the flavor, and every guess this design considered was
wrong on some real directory.

### 5.2 The detection ladder

Ordered, and it stops at the first match.

1. **`supportedCapabilities` contains `1.2.840.113556.1.4.800`** → **Active Directory Domain Services.**
   This is the reliable test (MS-ADTS 3.1.1.3.4.3, `LDAP_CAP_ACTIVE_DIRECTORY_OID`), and it is absent on
   AD LDS.
2. **`supportedCapabilities` contains `1.2.840.113556.1.4.1851`** → **AD LDS / ADAM.**
   Treated as an AD flavor for decoding purposes (it shares `objectSid`, `objectGUID`, and FILETIME
   semantics), but it has **no `defaultNamingContext`**, so §5.3 resolves its base from `namingContexts`.
3. **Otherwise → generic LDAPv3**, with a vendor hint when one is available.
   `vendorName` and `vendorVersion` (RFC 3045) are read and reported when present.

The third rung is explicitly a **heuristic, not a guarantee**, and the design says so rather than implying a
clean three-way classification.
OpenLDAP frequently does not populate `vendorName`, so a directory that is plainly OpenLDAP may report no
vendor at all.
When that happens, `server` prints the flavor as `ldapv3` with `vendor: unknown` and the supporting evidence
it does have (`supportedControl`, `supportedExtension`, `namingContexts`), rather than inventing a vendor
name.
Reporting `unknown` honestly is better than a confident wrong label, and no v1 behavior depends on
distinguishing OpenLDAP from 389 Directory Server.

Two further AD capability OIDs are reported by `server` when present, because they change what an operator can
expect, and are not used to make decisions in v1: `1.2.840.113556.1.4.1791` (LDAP signing and sealing) and
`1.2.840.113556.1.4.1920` (read-only domain controller).

A note that matters for §6.5: **there is no rootDSE attribute advertising supported matching rules.**
MS-ADTS states this explicitly.
So support for AD's extensible match rules is inferred from the AD detection above and from nothing else, and
§6.5 states what happens when that inference is wrong.

### 5.3 Base DN resolution, and never guessing

In precedence order:

1. `--base <dn>` on the invocation.
2. `base` in the selected profile, including `LDAP_AXI_BASE` for an env profile (§11.1).
3. **AD DS**: `defaultNamingContext` from the rootDSE.
4. **Any flavor**: the single value of `namingContexts`, when there is exactly one.
5. **Otherwise**: a `VALIDATION_ERROR` that lists the available naming contexts and tells the agent to pass
   `--base`.

Rung 5 is the load-bearing one.
A directory with several naming contexts has no correct default, and picking the first would silently scope
every subsequent query to an arbitrary partition, producing confidently incomplete answers.
AXI §5's principle that an ambiguous result causes a re-run with different flags applies with more force here,
because the agent would have no signal that anything was wrong.
So ambiguity is an error that names the choices:

```
error: several naming contexts are available and none is a default for this server
code: VALIDATION_ERROR
contexts[3]{dn}:
  "DC=example,DC=com"
  "CN=Configuration,DC=example,DC=com"
  "CN=Schema,CN=Configuration,DC=example,DC=com"
help[1]: "Run `ldap-axi entry search --base \"DC=example,DC=com\" --filter \"(objectClass=*)\"` with the context you want"
```

The reference implementation requires `base_dn` on every search and has no discovery at all (§1.1).
That is a defensible choice for a passthrough tool and a poor one for an agent-facing CLI, because it forces
the agent to already know the answer.
Discovery with an honest failure is the middle path.

### 5.4 Flavor-neutral and flavor-specific commands, stated per command

The design must state clearly which commands are which, so this is a table rather
than prose.

| Command | Neutral or specific | Behavior by flavor |
| --- | --- | --- |
| `entry search` | **Neutral** | Identical everywhere: the filter, base, scope, and attributes are the caller's. Only value rendering differs (§6.2, §6.3) |
| `entry show <dn>` | **Neutral** | Base-scope search on the DN |
| `server` | Neutral surface, flavor-shaped content | Reports whatever the rootDSE offers, plus AD-only attributes when AD is detected |
| `auth status` | Neutral | Who Am I when advertised; otherwise reports the bind DN as configured, not a resolved identity |
| `user list` / `user show` | **Specific** | AD: `(objectCategory=person)` with `sAMAccountName` / `userPrincipalName` identity resolution, decoded `userAccountControl` and timestamps. Generic: `(objectClass=inetOrgPerson)` or `posixAccount` with `uid` resolution, `entryUUID` and operational timestamps |
| `user groups` | **Specific** | AD: transitive, via `tokenGroups` or the `1941` rule (§6.4). Generic: direct only, merging `memberOf` with reverse-search results, with the method and completeness limitations reported (§7.2) |
| `group list` / `group show` | **Specific** | AD: `(objectCategory=group)`, with `groupType` decoded. Generic: `groupOfNames`, `groupOfUniqueNames`, or `posixGroup`, detected per entry (§7.2) |
| `group members` | **Specific** | AD: `--nested` supported. Generic: `member`, `uniqueMember`, or `memberUid` as the entry's class dictates, and `--nested` is refused with an explanation rather than silently ignored |
| `computer list` / `computer show` | **AD-first** | AD: `(objectCategory=computer)`. Generic: falls back to `(objectClass=device)` and names the fallback in output. An empty list establishes only that no visible entries matched under the selected base; it cannot distinguish absent entries, other object classes, and access-control restrictions (§13.6) |

The rule behind the table: **a flavor-specific command never silently produces a subtly different answer.**
Where the semantics genuinely differ, the output names what was done.
`user groups` on a generic directory without a `memberOf` overlay reports `transitive: false` and a
`method: reverse-search` field, so an agent asking "is this user an admin" cannot mistake a direct-membership
answer for a transitive one.
That single field is the difference between a correct answer and a security-relevant wrong one, and it is why
§7.2 exists as its own section.

Computer default and selectable fields are owned by `src/schema.ts` and exposed by `computer list --help` and `computer show --help`.
`--name`, AD-only `--sam`, `--filter`, `--scope`, paging bounds, `--fields`, and safe raw `--attributes` follow the existing typed-list contracts.
Computer details follow the binary and timestamp decoding contracts in §6.2 and §6.3.
Missing or ACL-hidden attributes are omitted.
Generic list and show results carry `fallback_filter: (objectClass=device)`; missing show identifiers remain `NOT_FOUND` with the fallback named.
An incomplete list never reports a definitive empty fallback.

### 5.5 Identifier resolution for `user show`, `group show`, and `computer show`

The identifier-resolution contract is: a syntactically valid distinguished
name and a bare identifier (`sAMAccountName`, `userPrincipalName`, `uid`, or `cn`) are resolved by exactly one
rule each, with no fallback ladder between them.

1. **A syntactically valid RFC 4514 DN** (recognized by a real recursive-descent parser, `src/directory/dn.ts`,
   not a shape heuristic) gets **one base-scope read at that DN**, filtered to require the command's object
   shape:
   - `user show`: AD/AD LDS `(objectCategory=person)`; generic LDAPv3
     `(|(objectClass=inetOrgPerson)(objectClass=posixAccount))`.
   - `group show`: AD/AD LDS `(objectCategory=group)`; generic LDAPv3
     `(|(objectClass=groupOfNames)(objectClass=groupOfUniqueNames)(objectClass=posixGroup))`.
   - `computer show`: AD/AD LDS `(objectCategory=computer)`; generic LDAPv3 `(objectClass=device)`.
   Zero matching entries, whether because the DN does not exist or because it exists but fails the shape
   filter, is `NOT_FOUND`.
   There is no fallback to a search.
2. **Anything else** gets **one exact, escaped subtree search** under the resolved base:
   - `user show`, AD/AD LDS: `(&(objectCategory=person)(|(sAMAccountName=<escaped>)(userPrincipalName=<escaped>)))`.
   - `user show`, generic: `(&(|(objectClass=inetOrgPerson)(objectClass=posixAccount))(uid=<escaped>))`.
   - `group show`, AD/AD LDS: `(&(objectCategory=group)(|(sAMAccountName=<escaped>)(cn=<escaped>)))`.
   - `group show`, generic: `(&(|(objectClass=groupOfNames)(objectClass=groupOfUniqueNames)(objectClass=posixGroup))(cn=<escaped>))`.
   - `computer show`, AD/AD LDS: `(&(objectCategory=computer)(|(sAMAccountName=<escaped>)(cn=<escaped>)))`.
   - `computer show`, generic: `(&(objectClass=device)(cn=<escaped>))`.
3. **Cardinality decides the outcome, and only cardinality:** zero matches is `NOT_FOUND`; exactly one is
   shown; two or more is `VALIDATION_ERROR` naming the identifier as ambiguous and requiring a DN.
   There is no preferred match, no second query with a different attribute, and no selector flag
   (`--sam`, `--upn`, `--uid`, `--cn`) added to the show commands in stage 2.
4. **Continuation references do not spoil that cardinality** (§9.6, answering §20.2's ninth question).
   A subtree search at an AD domain root always returns `SearchResultReference` messages for the
   configuration and DNS partitions, so counting one as an incomplete search made every identifier lookup at
   a domain root fail with `SERVER_LIMIT` while the DN path worked.
   A reference means the server answered in full for the naming context it holds and named subtrees it does
   not hold, so cardinality is counted over the entries that server returned, paging continues past a
   reference, and the references are reported in the `NOT_FOUND` help rather than chased.
   A terminal result code 10 is the different case - nothing was searched - and still raises `SERVER_LIMIT`,
   as do result codes 3, 4, and 11.

The rejected alternatives and why: preferring `sAMAccountName` over `userPrincipalName` on a collision is
convenient but silently wrong when the two values belong to different accounts; accepting only DNs is
unambiguous but breaks the `user show <sam>` shape the design already documents; and adding per-attribute
selector flags widens the show commands' surface beyond what stage 2 accepted.
The implementation is `src/directory/identity.ts`, shared by both commands.

## 6. Active Directory semantics

AD is first-class, which in practice means v1 decodes six things that a generic client leaves as opaque
integers and byte strings.

### 6.1 userAccountControl decoding

`userAccountControl` is an integer bitfield.
v1 reports the raw integer **and** the decoded flag names, because an agent can act on names and an operator
may need the number.

| Flag | Hex | Decimal |
| --- | --- | --- |
| `SCRIPT` | 0x0001 | 1 |
| `ACCOUNTDISABLE` | 0x0002 | 2 |
| `HOMEDIR_REQUIRED` | 0x0008 | 8 |
| `LOCKOUT` | 0x0010 | 16 |
| `PASSWD_NOTREQD` | 0x0020 | 32 |
| `PASSWD_CANT_CHANGE` | 0x0040 | 64 |
| `ENCRYPTED_TEXT_PWD_ALLOWED` | 0x0080 | 128 |
| `TEMP_DUPLICATE_ACCOUNT` | 0x0100 | 256 |
| `NORMAL_ACCOUNT` | 0x0200 | 512 |
| `INTERDOMAIN_TRUST_ACCOUNT` | 0x0800 | 2048 |
| `WORKSTATION_TRUST_ACCOUNT` | 0x1000 | 4096 |
| `SERVER_TRUST_ACCOUNT` | 0x2000 | 8192 |
| `DONT_EXPIRE_PASSWORD` | 0x10000 | 65536 |
| `MNS_LOGON_ACCOUNT` | 0x20000 | 131072 |
| `SMARTCARD_REQUIRED` | 0x40000 | 262144 |
| `TRUSTED_FOR_DELEGATION` | 0x80000 | 524288 |
| `NOT_DELEGATED` | 0x100000 | 1048576 |
| `USE_DES_KEY_ONLY` | 0x200000 | 2097152 |
| `DONT_REQ_PREAUTH` | 0x400000 | 4194304 |
| `PASSWORD_EXPIRED` | 0x800000 | 8388608 |
| `TRUSTED_TO_AUTH_FOR_DELEGATION` | 0x1000000 | 16777216 |
| `PARTIAL_SECRETS_ACCOUNT` | 0x04000000 | 67108864 |

**Two flags in that table are unreliable and v1 does not report them from this attribute.**
Microsoft states that on Windows Server 2003 and later domains, `LOCKOUT` and `PASSWORD_EXPIRED` in
`userAccountControl` are superseded by the computed attribute `msDS-User-Account-Control-Computed`.
So `user show` requests that computed attribute and reports `locked_out` and `password_expired` from it,
while `userAccountControl` supplies everything else.
A design that read lockout from the raw bitfield would be wrong on every modern domain, and it is the kind of
wrong that looks right in a fixture written by the same author.

`DONT_REQ_PREAUTH` and `TRUSTED_FOR_DELEGATION` are reported plainly rather than annotated.
They are security-relevant, an agent may well be looking for them, and editorializing in data output is not
this tool's job.

### 6.2 Binary attributes

Two AD attributes are binary and neither survives being treated as a string.
The reference implementation types every value as a Go `string` and therefore returns raw bytes (§1.1); that
is the specific failure this section avoids.

| Attribute | Canonical form | Raw form | Trap |
| --- | --- | --- | --- |
| `objectSid` | SDDL string, `S-1-5-21-…` | base64 | Rendering requires parsing revision, sub-authority count, 48-bit big-endian identifier authority, and little-endian sub-authorities |
| `objectGUID` | GUID string, `8-4-4-4-12` | base64 | AD's byte order is **mixed-endian**: the first three fields are little-endian, the last two big-endian. A straight hex dump does not match what AD tooling displays |
| `tokenGroups` | list of SDDL strings | base64 list | Constructed, binary SIDs; see §6.4 |

Both forms are emitted, named `objectSid` and `objectSid_raw`.
The canonical form is what an agent will use; the raw form exists because a correctness bug in the decoder
would otherwise be undetectable from the output, and because a base64 value is safe in TOON regardless of what
bytes it holds.
Any other attribute whose value is not valid UTF-8 is emitted base64 with a `_raw` suffix rather than being
lossily coerced, so a schema this design did not anticipate degrades honestly.

### 6.3 Timestamps, and the sentinels that break naive conversion

AD uses two time formats and v1 handles both.

**FILETIME** (`pwdLastSet`, `accountExpires`, `lastLogonTimestamp`, `lastLogon`, `lockoutTime`): 100-nanosecond
intervals since 1601-01-01 UTC.
Conversion is `unix_ms = ticks / 10000 - 11644473600000`.

Two sentinel values must not be converted:

- `0` means unset, and for `pwdLastSet` specifically it means "must change password at next logon".
  Converted naively it renders as 1601-01-01, which is not a date any operator wants to read.
- `9223372036854775807` (0x7FFFFFFFFFFFFFFF, `TIMEQ_FOREVER`) means never expires, and for `accountExpires`
  it is the common case.
  Converted naively it renders as a year-30828 date.

v1 renders these as `never` and `unset` respectively, as explicit strings, and never as a date.

**GeneralizedTime** (`whenCreated`, `whenChanged`): the RFC 4517 form, including reduced precision and a
fraction of the least-significant component, rendered as ISO 8601.

One honesty note that belongs in output rather than only in docs: `lastLogonTimestamp` is **deliberately
imprecise**.
It replicates, but AD only updates it when the stored value is older than `msDS-LogonTimeSyncInterval`
(default 14 days, minus a random fraction of 5 days), so it can be up to roughly two weeks stale.
`lastLogon` is precise but non-replicated and therefore per-domain-controller, meaning a query against one DC
does not see logons processed by another.
`user show` and `computer show` report `lastLogonTimestamp` with a `last_logon_precision: approximate` field rather than
presenting it as an exact time, because "when did this account last log in" is a question an agent will ask
and act on.

### 6.4 Nested group expansion

Transitive group membership is where AD's first-class treatment pays off, and there are two routes with
different costs.

| Route | Mechanism | Cost | Limits |
| --- | --- | --- | --- |
| `tokenGroups` | Constructed attribute, base-scope read on the principal, returns transitive group SIDs including the primary group | One read, cheap | Binary SIDs needing §6.2 decoding, then a second lookup per SID to get names; cannot be used in a search filter |
| `1.2.840.113556.1.4.1941` | `LDAP_MATCHING_RULE_IN_CHAIN` extensible match, walks the DN chain transitively | One search, potentially expensive on a large directory | Returns DNs directly; AD-only |

v1 uses `tokenGroups` as the default for `user groups`, because one base-scope read plus a SID resolution pass
is cheaper and more predictable than a chain walk, and because it is the only route that includes the primary
group.
`--nested` on `group members` uses the `1941` rule, because the question there is "who is in this group" and
that direction has no `tokenGroups` equivalent.
AD does not represent a principal's primary-group membership in `member` or `memberOf`, so both direct and
nested `group members` results explicitly report `partial: true` with
`stop_reason: primary_group_members_not_included` rather than claiming a complete answer.

**`primaryGroupID` is the trap that makes this section necessary.**
`memberOf` is a computed back-link that does **not** include the user's primary group, which for a typical
user is Domain Users (RID 513).
So "list this user's groups" via `memberOf` silently omits a group the user is genuinely in.
Resolving it requires combining `primaryGroupID` with the domain SID.
v1's `tokenGroups` default sidesteps this because `tokenGroups` includes the primary group; when v1 falls back
to `memberOf` (a server that does not return `tokenGroups`), it resolves `primaryGroupID` explicitly and marks
the result `method: memberOf+primaryGroupID` so the output says how the answer was assembled.

`memberOf` also does not reliably cross domain boundaries in a multi-domain forest.
v1 does not solve that in this release; §1.3 defers Global Catalog search, which is the mechanism that would,
and §20 records it as an open question rather than leaving the gap unstated.

### 6.5 AD extensible match rules

Syntax is `(<attribute>:<ruleOID>:=<value>)`, and the value is **decimal** for the bitwise rules.

| OID | Name | Semantics | Example |
| --- | --- | --- | --- |
| `1.2.840.113556.1.4.803` | `LDAP_MATCHING_RULE_BIT_AND` | true when **all** bits in the value are set | `(userAccountControl:1.2.840.113556.1.4.803:=2)` finds disabled accounts; `(!(userAccountControl:1.2.840.113556.1.4.803:=2))` finds enabled ones |
| `1.2.840.113556.1.4.804` | `LDAP_MATCHING_RULE_BIT_OR` | true when **any** bit in the value is set | `(userAccountControl:1.2.840.113556.1.4.804:=18)` finds locked-out or disabled |
| `1.2.840.113556.1.4.1941` | `LDAP_MATCHING_RULE_IN_CHAIN` | walks the DN chain transitively | `(memberOf:1.2.840.113556.1.4.1941:=CN=Admins,OU=Groups,DC=example,DC=com)` finds nested members; reversing the attribute to `member` finds a principal's nested groups |

v1 composes these itself for `--disabled`, `--enabled`, `--locked`, and `--nested`, so an agent gets the
common cases without knowing the OIDs, and `entry search --filter` still accepts them directly for the cases
v1 does not model.

Verified locally: `ldapts@9.0.0`'s `FilterParser.parseString` round-trips
`(memberOf:1.2.840.113556.1.4.1941:=CN=G,DC=x)` unchanged, so the extensible-match syntax survives the parse
step that §8.3 requires.

Two limits stated rather than assumed.
There is no rootDSE attribute advertising matching-rule support (§5.2), so v1 offers these flags only when AD
was detected, and a server that reports AD but rejects the rule surfaces the server's own error translated per
§12, not a silent empty result.
The `1941` rule can be expensive on a large directory, which is a second reason `user groups` prefers
`tokenGroups` (§6.4).

### 6.6 AD bind sub-error codes

AD returns result code 49 for nearly every bind failure and packs the real reason into the diagnostic message:

```
80090308: LdapErr: DSID-0C09030B, comment: AcceptSecurityContext error, data 52e, v1db1
```

v1 extracts the `data <hex>` token and translates it:

| `data` | Meaning | ldap-axi code (§12.2) |
| --- | --- | --- |
| `525` | user not found | `AUTH_FAILED` |
| `52e` | valid user, wrong password | `AUTH_FAILED` |
| `52f` | account restriction, for example blank password not allowed | `AUTH_FAILED` |
| `530` | not permitted to log on at this time | `AUTH_FAILED` |
| `531` | not permitted to log on at this workstation | `AUTH_FAILED` |
| `532` | password expired | `PASSWORD_EXPIRED` |
| `533` | account disabled | `ACCOUNT_DISABLED` |
| `568` | too many context ids | `AUTH_FAILED` |
| `701` | account expired | `ACCOUNT_EXPIRED` |
| `773` | must reset password at next logon | `PASSWORD_EXPIRED` |
| `775` | account locked out | `ACCOUNT_LOCKED` |

The distinct codes exist because the remedies differ: a locked-out account needs an administrator, an expired
password needs a password change elsewhere, and a wrong password needs a different credential.
Collapsing all of them to `AUTH_FAILED` would tell an agent to retry, which §2.3 forbids.

**Sourcing note, stated because it affects how much this table should be trusted.**
Microsoft documents the *mechanism* (MS-ERREF's LDAP-to-Win32 mapping) but publishes no single consolidated
table of these sub-codes.
The table above is reproduced from Broadcom KB 51487 and LDAPWiki, which agree with each other and with
widespread operational practice.
It is high-confidence operational fact rather than a primary-source specification, the parser therefore treats
an unrecognized `data` value as `AUTH_FAILED` with the raw token reported, and §20 records confirming the
table against a real domain controller as an open item.
An unrecognized sub-code must never crash and must never be silently dropped.

### 6.7 `groupType` decoding: raw, normalized, typed, and lossless

The AD `groupType` decoding contract follows.
`groupType` is a signed 32-bit LDAP integer (MS-ADTS `groupType` constants).
The five scope/application bits are documented as mutually exclusive.
`BUILTIN_LOCAL` is an orthogonal, system-only flag that can accompany another group-type flag on a system-created Builtin object.
`SECURITY_ENABLED` may combine with `BUILTIN_LOCAL`, `GLOBAL`, `DOMAIN_LOCAL`, or `UNIVERSAL`, but not with either application type.
v1 decodes it losslessly rather than collapsing it to a single label, because a malformed or unexpected
combination is directory data, not invalid CLI input, and rejecting it would hide an observable server state.

| Bit | Hex | Name |
| --- | --- | --- |
| Builtin local | `0x00000001` | `BUILTIN_LOCAL` |
| Global | `0x00000002` | `GLOBAL` |
| Domain local | `0x00000004` | `DOMAIN_LOCAL` |
| Universal | `0x00000008` | `UNIVERSAL` |
| Application basic | `0x00000010` | `APPLICATION_BASIC` |
| Application query | `0x00000020` | `APPLICATION_QUERY` |
| Security-enabled | `0x80000000` | `SECURITY_ENABLED` |

`group show` on AD and AD LDS reports every one of these, computed from one decode:

- `group_type_raw`: the original signed LDAP integer.
- `group_type_unsigned`: the same bits, normalized as an unsigned 32-bit integer (`raw >>> 0` in JavaScript),
  because bit inspection on a negative signed integer is exactly the kind of arithmetic a future contributor
  gets wrong by hand.
- `group_scope`: one of `global`, `domain_local`, `universal`, `application_basic`, `application_query`, or
  `unknown`.
  It is the single scope/application bit's name when exactly one is set, and `unknown` otherwise; it is never
  guessed from a majority or a preferred bit.
  `BUILTIN_LOCAL` does not participate in scope selection.
- `security_enabled` and `builtin_local`: booleans from their respective bits.
- `group_type_flags`: the ordered list of known bit names actually set, in the fixed order
  `BUILTIN_LOCAL, GLOBAL, DOMAIN_LOCAL, UNIVERSAL, APPLICATION_BASIC, APPLICATION_QUERY, SECURITY_ENABLED`.
- `group_type_unknown_bits`: any bit outside the known mask `0x8000003f`, reported as a hex string and never
  silently discarded or reinterpreted; omitted when there are none.
- `group_type_anomalies`: present when zero or more than one scope/application bit is set (for example
  `"multiple scope bits: GLOBAL,UNIVERSAL"`) or when `SECURITY_ENABLED` accompanies an application type.
  These are real, reportable server-data anomalies rather than CLI validation failures.
- `group_type_valid`: `true` only when there are no unknown bits, exactly one scope/application bit is set, and
  an application type is not security-enabled.
  A `false` value never blocks the read; the entry is still returned in full.

`groupType` has no analogue in generic LDAPv3 (`groupOfNames`, `groupOfUniqueNames`, and `posixGroup` carry no
equivalent attribute), so every field in this section is omitted, never emitted as `null` or `unknown`, on a
generic directory.
The implementation is `src/directory/grouptype.ts`.

## 7. Generic LDAPv3 semantics

Generic LDAPv3 is not a degraded AD.
It has its own attributes and its own group models, and the places where it is genuinely *less* capable are
stated as such rather than papered over.
The `user` commands select `inetOrgPerson` or `posixAccount` entries.
Their help directs operators to `entry search` for non-person service accounts such as `account` plus `simpleSecurityObject`.

### 7.1 Operational attributes

Operational attributes are not returned by default and not covered by `*` (RFC 4512 §3.4, §5.1).
v1 requests them by name.

| Attribute | Spec | AD analogue |
| --- | --- | --- |
| `entryUUID` | RFC 4530 | `objectGUID`, but a **string**, not binary, so no §6.2 decoding |
| `entryDN` | RFC 5020 | `distinguishedName` |
| `createTimestamp` / `modifyTimestamp` | RFC 4512 §5.1 | `whenCreated` / `whenChanged`, and both are GeneralizedTime |
| `creatorsName` / `modifiersName` | RFC 4512 §5.1 | no direct analogue |
| `subschemaSubentry` | RFC 4512 | same attribute name |

The `+` pseudo-attribute that requests all operational attributes is a widespread convention rather than an
RFC-standard one, so v1 requests operational attributes by name and does not depend on `+`.
In OpenLDAP the four timestamp and modifier attributes are gated by the `lastmod` slapd option, so their
absence is a server configuration fact rather than an error, and v1 omits an absent attribute rather than
emitting a null.

`user show` and `user list` explicitly request `pwdAccountLockedTime` for generic account state.
OpenLDAP's permanent administrative-lock sentinel `000001010000Z`, including equivalent GeneralizedTime representations, reports `enabled: false`, `locked: true`, and `account_state.locked_out: true`.
Other values appear as `account_state.pwd_account_locked_time` with `locked_out: unknown`.
A timed lock can expire without the timestamp being removed, and its effective `pwdLockoutDuration` can come from an unreadable server-default policy.
v1 therefore never infers a current lock from an ordinary timestamp or an enabled account from an absent or ACL-hidden attribute.
The `enabled`, `locked`, and `account_state` fields are selectable and included in generic defaults, with unknown scalar booleans omitted.

Generic `--disabled`, `--enabled`, and `--locked` first read `subschemaSubentry` (rootDSE, or the search base if rootDSE omits it) and the schema entry's `attributeTypes`.
Without a readable `pwdAccountLockedTime` definition they fail with `UNSUPPORTED_BY_SERVER`.
`--disabled` selects the permanent sentinel, `--enabled` excludes that sentinel, and `--locked` selects recorded lock candidates by attribute presence.
The help explains these observable ppolicy semantics: they do not prove an account can authenticate or that ACLs revealed every lock.
If `--locked` returns a candidate without a readable permanent sentinel, the result reports `partial: true` and `account_state_incomplete: lockout_policy_unavailable` separately from pagination metadata.
No policy guessing, authentication attempts, or password reads are used to determine state.
The sentinel and timed-lock caveat are documented by [OpenLDAP's ppolicy manual](https://www.openldap.org/software/man.cgi?query=slapo-ppolicy&sektion=5) and [the OpenLDAP maintainers' lock-state discussion](https://www.openldap.org/lists/openldap-technical/201606/msg00038.html).

### 7.2 The three group shapes, and no portable nesting

This is the largest genuine divergence between the two targets, and getting it wrong produces
security-relevant wrong answers, so it is stated as a table plus a rule.

| Class | Membership attribute | Value form |
| --- | --- | --- |
| `groupOfNames` | `member` | DN |
| `groupOfUniqueNames` | `uniqueMember` | name and optional UID |
| `posixGroup` | `memberUid` | **bare username string, not a DN** |

`group members` detects the entry's class and reads the matching attribute.
A `posixGroup` returning bare usernames cannot be resolved to DNs without a second search per name, and v1
reports the usernames as they are with a `member_form: uid` field rather than fabricating DNs.
These unverified references carry `type: unresolved`, including names that might no longer identify an entry.

Two hard limits, both reported in the output rather than only documented:

- **`memberOf` is not standard.**
  In OpenLDAP it requires the `memberof` overlay to be configured.
  Without it, the only way to answer "what groups is this user in" is a reverse search
  `(&(objectClass=groupOfNames)(member=<userDN>))`.
  An overlay can cover only some group classes, so v1 always reverse-searches `member`, `uniqueMember`, and, when the user has a `uid`, `memberUid`.
  It merges those results with readable `memberOf` references, deduplicates DNs within one shared row budget, and reports `method: memberOf+reverse-search` or `reverse-search`.
  Equality on `uniqueMember` includes its optional UID suffix, so a DN-only reverse search cannot exclude suffix-bearing memberships.
  Generic results therefore remain partial with `stop_reason: unique_member_uid_not_checked` unless another limit or referral already explains the partial read.
  The help names that gap rather than suggesting a larger row budget could close it.
- **There is no portable nested-group expansion.**
  `1.2.840.113556.1.4.1941` is AD-only.
  On a generic directory, `--nested` is **refused with an explanation**, not silently ignored, because AXI §6
  is explicit that a silently dropped flag is worse than an error: the agent would receive a
  direct-membership answer while believing it was transitive.

```
$ ldap-axi user groups uid=alice --nested
error: this server does not support transitive group expansion
code: UNSUPPORTED_BY_SERVER
help[2]: "Active Directory supports nested expansion; this server was detected as ldapv3","Run `ldap-axi user groups uid=alice` for direct memberships, which will report method and transitive:false"
```

Every `user groups` and `group members` result carries `transitive: true|false`.
That field is the whole point of this section.

### 7.3 posixAccount and posixGroup

RFC 2307 and RFC 2307bis (`nis.schema`) attributes are recognized by `user show` on a generic directory:
`uid`, `uidNumber`, `gidNumber`, `homeDirectory`, `loginShell`, `gecos`.
RFC 2307bis adds DN-valued `member` through `groupOfNames`, which is why §7.2 detects per entry rather than
per server: one directory can carry both shapes.

## 8. Injection safety: DN and filter escaping

LDAP filter injection deserves the seriousness given to SQL injection, and this section exists because the
chosen library contains a trap that fails **silently**.

### 8.1 The `escapeFilter` trap, verified locally

`ldapts` exports `escapeFilter`, which reads like a value escaper and is not: it is a **tagged template
function**, and it is the only escaping helper the library exports.

Verified locally on `ldapts@9.0.0`:

```js
const evil = 'a*b(c)|&d\\e\u0000f';

escapeFilter`(cn=${evil})`   // → "(cn=a\\2ab\\28c\\29|&d\\5ce\\00f)"   correct
escapeFilter(evil)           // → "a"                                    silently wrong
```

The correct tagged form escapes per RFC 4515.
The plain-function misuse returns `"a"`, because a string passed where a `TemplateStringsArray` is expected
makes `strings[0]` the string's **first character**.
It does not throw.
It does not warn.
It returns a filter fragment that is one character long, and a caller that concatenated it into a filter would
issue a syntactically valid search with completely wrong semantics.

This is exactly the class of finding the fleet has recorded before in a different form: `azure-axi`'s lesson
that a dependency's real surface must be verified by importing it rather than read from its declarations.
Here the declaration is honest and the **call shape** is the trap.

### 8.2 The project-owned escapers

Because of §8.1, v1 does not depend on the library's helper as its safety boundary.

- **`filterValue(value: string): string`** hex-escapes per RFC 4515: `*` → `\2a`, `(` → `\28`, `)` → `\29`,
  `\` → `\5c`, NUL → `\00`, and any other octet that needs escaping, octet by octet for multi-byte UTF-8.
  It is unit-tested against the byte table directly, not against the library.
- **`dnValue(value: string): string`** escapes per RFC 4514 using the **hex form for everything
  questionable** rather than the backslash shorthand, because the hex form is always valid while the
  shorthand is permitted only for a specific character set.
  It also handles the positional rules the shorthand-only implementations get wrong: a leading `#`, a leading
  space, and a **trailing** space must be escaped even though the same characters are legal mid-value.
- Every convenience flag (`--user`, `--group`, `--name`, `--sam`, `--upn`, `--uid`) interpolates through
  `filterValue`, and every DN argument through `dnValue`.
  There is no path from user input to a filter that skips them.
- A lint rule rejects any **non-tagged reference** to the library's `escapeFilter`, so the §8.1 misuse cannot
  appear in this codebase even as a convenience.
- A test asserts that `filterValue` applied to `*` produces `\2a`, which is the assertion that catches a
  future refactor swapping in the library helper as a plain function.

One deliberate non-escape: an intentional substring wildcard.
`user list --name "smi*"` is a wildcard search, and escaping the `*` would break it.
So wildcards are a property of the **flag's contract**, not of the value: flags that accept a wildcard say so
in their help, and they split the value on `*`, escape each literal segment, and rejoin with an unescaped `*`.
Escaping must happen at the value-interpolation boundary and never as a pass over an assembled filter string.

### 8.3 `--filter` is parsed, not concatenated

`entry search --filter` accepts a raw RFC 4515 filter, because §1.2 requires an escape hatch and a filter is
the caller's to own.

It is still not passed through blindly.
The filter is **parsed** with `FilterParser.parseString` before anything is sent, so a malformed filter is a
`VALIDATION_ERROR` naming the syntax problem rather than a protocol error from the server or, worse, a
successful search of something unintended.
Verified locally that the parser round-trips both an ordinary filter and an AD extensible-match filter
(§6.5).

And `--filter` is never combined with convenience flags by string concatenation.
When both are present, the parsed filter and the flag-derived clauses are combined as **parsed filter objects**
under an `AND`, so there is no textual seam where a crafted `--filter` value could escape its own parentheses
and alter the surrounding structure.

## 9. Paging, limits, and truncation honesty

### 9.1 The silent-truncation default

**This is the most dangerous default in LDAP, and it is why §2.1 registers no unpaged search.**

Active Directory's `MaxPageSize` LDAP policy defaults to **1000** (MS-ADTS 3.1.1.3.4.6).
A search that would return more than that, issued **without** the RFC 2696 paged results control, returns the
first 1000 entries.
Microsoft's own guidance is that a search which may exceed `MaxPageSize` must use the paged control.

The failure mode is not an error.
It is a plausible-looking result set that is quietly incomplete.
An agent asked "how many disabled accounts are there" would answer 1000 and be wrong, with nothing in the
output to suggest it.

The reference implementation's default makes this concrete: `page_size` defaults to 0, which **disables
paging** (§1.1), so its default configuration is the silently-truncating one.

### 9.2 Always paged, one page at a time

v1 paginates unconditionally.
There is no flag to disable paging.

The implementation constraint is verified: `ldapts` has two search shapes and only one is acceptable.

| Method | Shape | Verdict |
| --- | --- | --- |
| `search(base, options)` | Returns a buffered `Promise<SearchResult>`; with `paged: true` it follows every cookie internally and accumulates every entry into one array | **Never used.** Unbounded memory on a large directory, and it hides the page boundary that §9.3 needs |
| `searchPaginated(base, options)` | `AsyncGenerator<SearchResult>`, one page per yield | **The only search path in v1** |

`Directory.searchPages` (§3.3) is an async iterable of pages for exactly this reason: the sealed client cannot
offer a "give me everything" method, because such a method could not report partiality.

Page size is `min(--page-size, server MaxPageSize when known, 1000)`, defaulting to 1000 on AD and 500
elsewhere.
`ldapts`'s own default is 100, which is a needless four-fold round-trip cost against AD's 1000 ceiling.

### 9.3 Partial results and stop reasons

A capped read cannot be mistaken for a complete one.
The shape follows `falcon-axi` §7.2 so the fleet's partial-result contract is one contract:

```
$ ldap-axi user list --disabled --all --max-rows 2
count: 2 of unknown total
partial: true
stop_reason: max_rows
users[2]{sam,name,enabled,last_logon}:
  jdoe,"Doe, John",false,"2026-06-14T08:21:00Z"
  asmith,"Smith, Alice",false,never
help[1]: "Narrow the filter or base and re-run with `--all --max-rows <n>` for another bounded read"
```

`stop_reason` is one of:

| Reason | Meaning |
| --- | --- |
| `max_rows` | The caller's row budget was spent |
| `server_size_limit` | Result code 4, `sizeLimitExceeded`: the server's own cap stopped it (§9.5) |
| `server_admin_limit` | Result code 11, `adminLimitExceeded`: an administrative policy stopped it |
| `server_time_limit` | Result code 3, `timeLimitExceeded` |
| `page_boundary` | The default one-page read has a continuation, reported as `incomplete: page_boundary` rather than a partial result |

A complete read emits no `partial` marker at all, so its absence is meaningful.

`count: N of M total` needs a caveat that HTTP-shaped siblings do not have: **LDAP has no total count.**
There is no equivalent of `meta.pagination.total`; the only way to know how many entries match is to walk
every page.
So `M` is populated only when the walk actually completed, or when a prior `--count`-style walk supplied it.
Otherwise the line reads `count: N of unknown total`, never a fabricated number.
This is a real ergonomic loss against the sibling CLIs and it is stated rather than papered over; a directory
CLI that invented a total would be lying about the one number an agent is most likely to quote.

### 9.4 Paging is in-process only

RFC 2696's cookie is an **opaque, server-scoped** octet string.
The maintained `ldapts` public API follows it within one `searchPaginated()` invocation but does not expose a
request or response cookie.
So v1 deliberately does not support cross-invocation continuation, emits no continuation token, and rejects
`--cursor` as out of scope.

This preserves the sealed client boundary and avoids depending on private library internals.
The reliable bounded path for a large read is a **single-invocation walk**: `--all --max-rows <n>`, which keeps
one connection open and follows pages in process.
The default retains one page and advances the public iterator once to distinguish exhaustion from a continuation.
On exhaustion that advance performs no network I/O; a continuation fetches one additional page whose entries are discarded.
Only a continuation produces `incomplete: page_boundary`; a terminal first page reports a complete total or a definitive empty state.
Any limit or referral on the lookahead is still reported.

A future version may revisit resumable cursors only if its maintained client exposes the RFC 2696 request and
response cookie through a supported public API.
That work must retain context binding and must never restart a rejected cursor silently.

### 9.5 Server limits, and result codes that mean "partial", not "failed"

Three limits can stop a search that ldap-axi did not stop, and all three arrive as result codes:

| Code | Name | Meaning here |
| --- | --- | --- |
| 4 | `sizeLimitExceeded` | The server returned some entries and then stopped. **AD returns partial results with this code.** |
| 11 | `adminLimitExceeded` | An administrative policy cap, for example AD's `MaxQueryDuration` or `MaxTempTableSize` |
| 3 | `timeLimitExceeded` | The server's time limit, or the `timeLimit` v1 requested |

**The entries already yielded from complete pages are real data and must be returned**, with `partial: true`
and the matching `stop_reason`, at exit 0.
Reporting them without the marker would present a truncated answer as complete.
`ldapts@9.0.0` checks the terminal result code before exposing entries carried in that same response, so those
terminal-response entries cannot be retained through its supported public API.
ldap-axi does not reach into the client's private `_send` path to recover them.
A limit hit before any complete page was retained is therefore an error at exit 1, mirroring `falcon-axi`'s
rule that a wall reached with rows retained is a partial result while a wall reached with nothing retained is
a failure.

v1 sets a server-side `timeLimit` alongside the client-side socket deadline.
The reference implementation hardcodes `timeLimit` to 0 and relies on a socket timeout, which abandons the
client's wait without telling the server to stop working; setting both means an expensive query is bounded on
the server too.

Verified locally, `ldapts@9.0.0` accepts both `timeout` (per-operation, milliseconds) and `connectTimeout`,
and **both default to 0, meaning no timeout**.
v1 sets both explicitly.
A CLI that inherits those defaults hangs indefinitely against an unreachable or wedged directory, which is
unacceptable for a tool an agent invokes.

`ldapts` also exposes no idle timeout and no reconnect-with-backoff policy; reconnection is implicit on the
next operation.
Combined with `autoRebind` being off (§2.3), v1's model is one connection for one invocation, and a dropped
connection is a translated error rather than a transparent retry.

### 9.6 Referrals are reported, never chased

AD returns continuation references (result code 10, and `SearchResultReference` messages) when a search
crosses a naming context boundary.

Verified from the library's behavior: `ldapts` collects reference messages and flattens their URIs into
`SearchResult.searchReferences`, and **never follows them**.
For a terminal result code 10, however, `ldapts@9.0.0` discards the protocol referral field and exposes only an
`UnknownStatusCodeError`.
ldap-axi still reports that search as partial with `stop_reason: referral` rather than aborting or claiming
completeness, but it can emit URIs only when the server sent `SearchResultReference` messages through the
supported public API.

That is the correct default for a read-only CLI and v1 keeps it.
Chasing a referral would silently fan out to other directory servers the operator did not name, against
credentials the operator scoped to one server, which is a genuine security concern and not merely a
performance one.
So referrals are surfaced as data:

```
referrals[1]{uri}:
  "ldap://child.example.com/DC=child,DC=example,DC=com"
help[1]: "Run the same search against that server with `--url ldap://child.example.com` to include its results"
```

An agent can then decide, with the operator's credentials, whether that second server is in scope.

The same rule governs identifier resolution: a reference names an unsearched subtree, not an unreliable
answer, so `user show` and `group show` count only the entries the searched server returned and report the
references alongside a `NOT_FOUND` (§5.5).

## 10. Transport security and TLS

### 10.1 LDAPS and StartTLS, and what v1 defaults to

| | LDAPS | StartTLS |
| --- | --- | --- |
| Port | 636 (3269 for Global Catalog) | 389 |
| Standard | **Not standardized in any RFC**; historical and universally implemented | RFC 4511 §4.14, OID `1.3.6.1.4.1.1466.20037`, security in RFC 4513 |
| Handshake | Implicit TLS from the first byte | Plaintext, then upgrade |

There is a genuine split here and the design states it as a split rather than resolving it by fiat.
The historical IETF position, and OpenLDAP's own FAQ, favor StartTLS and call `ldaps://` deprecated.
The modern security position runs the other way: implicit TLS has no unprotected pre-upgrade phase to strip or
inject into, and RFC 8314 establishes that preference for implicit TLS on dedicated ports in a
protocol-general argument.

**v1 defaults to `ldaps://` on 636 with full certificate verification**, supports `--start-tls` on 389
explicitly, and **refuses plaintext by default**.
Plaintext simple or anonymous binds require the per-invocation `--insecure-plaintext` flag and print a warning on stderr.
A selected GSSAPI plan is the one exception, because §10.7's sealed plaintext transport encrypts every
post-bind LDAP PDU itself; it never relaxes the flag for anonymous or simple binds.
Likewise, the TLS-verification-disabled warning applies only to simple or anonymous TLS invocations; a refused GSSAPI invocation does not claim verification was disabled.

The reasoning for the default over the historical preference: ldap-axi's credential is a bind password sent on
the same connection, an agent may be pointed at an arbitrary URL, and the downgrade surface is the risk that
matters most in that setting.

### 10.2 The custom CA problem, and a local trap proved by measurement

A corporate proxy can TLS-intercept some endpoints while Node ships its own CA bundle.
That concern transfers to LDAPS, though not by the same mechanism: an HTTP-intercepting proxy does not
generally sit in front of port 636, but a corporate directory's certificate is very often issued by a
**corporate internal CA that Node does not trust**, which produces an identical symptom.

Measured on the development machine during this design task:

| Observation | Result |
| --- | --- |
| Node's bundled root store | 120 certificates, **zero** matching the corporate root CA |
| System store `/etc/ssl/certs/ca-certificates.crt` | 122 certificates, corporate root CA **present** |

So a Node LDAPS client on this machine cannot validate a certificate issued by the corporate root CA with default trust, while
`openssl` and `curl` can.
That is the same shape as the recorded azure-axi finding that Node `fetch` rejects a chain `curl` accepts.

**The trap, proved rather than assumed.** Two ways to add a CA behave differently:

```
tls.connect({ host: 'registry.npmjs.org', ... })                    → authorized: true
tls.connect({ host: 'registry.npmjs.org', ca: <corporate root CA only> }) → UNABLE_TO_GET_ISSUER_CERT_LOCALLY
NODE_EXTRA_CA_CERTS=<corporate root CA file> node … tls.connect({ host: … }) → authorized: true
```

`tlsOptions.ca` **replaces** Node's default trust store; `NODE_EXTRA_CA_CERTS` **extends** it.

So the obvious implementation of a `--ca-file` flag - pass the file as `tlsOptions.ca` - would silently
**narrow** trust to that one CA.
For a single-purpose LDAPS connection that happens to work, and it is still the wrong shape: it means a
directory whose chain roots in a public CA stops validating the moment an operator adds a corporate CA for a
different server, and the failure looks like a certificate problem on the server rather than a configuration
problem in the tool.

**v1's rule:** `--ca-file` and its config equivalent **append** to the platform trust store.
The implementation reads the PEM and passes `ca: [...tls.rootCertificates, ...extraPems]`, so added CAs are
additive and never subtractive.
`--ca-only` exists for the deliberate case where an operator wants exactly one trust anchor and nothing else,
and it says so in its help.
`auth status` reports which mode is active, because "why does this validate on my colleague's machine" is
otherwise unanswerable.
`NODE_EXTRA_CA_CERTS` continues to work because it is Node's own mechanism, and the README documents it as the
zero-configuration path.
An unreadable `--ca-file` is a `VALIDATION_ERROR` with a path and permissions remedy, before any connection opens.
Combining an `ldaps://` URL with `--start-tls` is also refused as `VALIDATION_ERROR` before connection.

### 10.3 The StartTLS hostname-verification trap, verified in source

Verified locally in `ldapts@9.0.0` `src/Client.ts`, `startTLS` sets `options.socket = originalSocket` (line
285) and passes that options object to `tls.connect`.

On this path the socket is already connected, and the library supplies no host identity.
**Certificate identity verification therefore depends on the caller supplying the URL host explicitly.**

v1 passes `host` on both TLS paths, set to the URL hostname without IPv6 brackets, so socket-based StartTLS retains certificate identity verification.
For DNS hosts it also passes `servername`; for IP literals it omits SNI to avoid Node's DEP0123 warning while still checking the certificate's IP identity.
Without that host identity, a StartTLS connection could validate a certificate chain while never checking the certificate
belongs to the server actually contacted, which is a silent downgrade of exactly the protection StartTLS
exists to provide.
§20 records confirming the behavior against a real StartTLS endpoint, because reading the source establishes
what is passed and only a live test establishes what Node concludes from it.

### 10.4 The `tlsOptions`-forces-implicit-TLS trap

Verified in the same source: `ldapts` sets `this.secure = isSecureProtocol || hasTlsOptions`.

So supplying a non-empty `tlsOptions` alongside an `ldap://` URL makes the client attempt **implicit** TLS on
port 389, which a plaintext LDAP port will not answer.
An operator who passes `--ca-file` with `--start-tls` would hit a confusing connection failure, because the
CA option would have quietly changed the connection mode.

v1's construction rule follows from that: TLS options are passed to the client constructor **only** for an
`ldaps://` URL, and on the StartTLS path they are passed to `startTLS()` instead, with the host identity
options from §10.3.
A test covers both paths, because this is the kind of trap that a working manual test on one URL scheme hides
completely.

The optional `--tls-max-version 1.2` flag, its `tlsMaxVersion` config key, and `LDAP_AXI_TLS_MAX_VERSION`
environment setting cap verified LDAPS or StartTLS at TLS 1.2 for legacy directory endpoints whose TLS 1.3
negotiation is incompatible.
The omitted default leaves Node's normal TLS version negotiation unchanged.
The value is validated before networking, and the cap is never applied to plaintext LDAP.
This is a single explicit transport setting, not a negotiate-then-retry downgrade, so it preserves the one
exchange and no-fallback contracts.

### 10.5 `--tls-no-verify`

Verification bypass exists for explicit anonymous reads, because real corporate directories have self-signed certificates and an operator sometimes must read one today.
Simple and GSSAPI authentication reject it before binding.
Its shape is deliberately inconvenient:

- **Per-invocation only.**
  Not settable from the config file and not from an environment variable, so it can never be a machine's
  quiet default.
- **Warns on stderr**, where agents do not read, so it cannot pollute structured output.
- **Reports `tls_verified: false` in the output data**, where agents do read.
  This is the important half: an agent that receives directory contents can tell they came over an
  unverified channel and can decline to act on them.
- Named `--tls-no-verify`, not `--insecure`, because it says what it turns off.

The reference implementation's silent `-insecure` is the shape being avoided: it changes a security property
with no trace in the output.

### 10.6 GSSAPI provider foundation and channel protection

The exact-pinned `kerberos@7.0.0` source provider loads only through `src/directory/gssapi.ts`.
The in-repository package carries the upstream source and a narrow native patch because the unmodified provider does not expose GSS `conf_state` or consume application channel-binding data.
The ldap-axi package root owns its build and package-relative loader, verifies prebuilds against its package-pinned SHA-256 manifest, and never resolves a registry or hoisted `kerberos` package.
The installer and synchronous provider loader share one package-relative target and native-mode decision, positively reject musl, and otherwise permit the Linux glibc x64 prebuild when a runtime omits its glibc report field.
A verified bundled prebuild is atomically installed at `build/Release` before auto mode considers source compilation, and `build/native-status.json` records that outcome.
That record is the loader's source of truth: a recorded `unavailable` result is refused with its recorded detail, a recorded `installed` result loads `build/Release/kerberos.node` and refuses when that artifact is absent, and only a missing status file admits the bundled fallback, which repeats the same mode, target, manifest, and digest checks before loading the bundled artifact.
The adapter selects one URL-derived target and defers context preparation until the selected transport is ready, so a TLS transport can supply channel-binding data before the first context token.
The maintained native patch preserves unsigned GSS major/minor statuses and SSPI status on error objects at the N-API boundary.
The adapter maps `GSS_S_NO_CRED`, MIT `KRB5_FCC_NOFILE`/`KRB5_CC_NOTFOUND`, `GSS_S_CREDENTIALS_EXPIRED`, MIT `KRB5KRB_AP_ERR_TKT_EXPIRED`, and SSPI `SEC_E_NO_CREDENTIALS`/`SEC_E_CONTEXT_EXPIRED` by numeric code to `GSSAPI_CREDENTIAL_UNAVAILABLE`.
This applies to initialization, the first token, and continuation steps, and recommends `kinit` on Linux or domain sign-in on Windows.
Other initialization failures retain `GSSAPI_PREPARATION_FAILED`; native prose is never parsed or exposed.
The numeric mappings follow the [MIT GSS status definitions](https://github.com/krb5/krb5/blob/master/src/lib/gssapi/generic/gssapi.hin), [MIT Kerberos error table](https://github.com/krb5/krb5/blob/master/src/lib/krb5/error_tables/krb5_err.et), and [Microsoft SSPI status table](https://learn.microsoft.com/en-us/windows/win32/com/com-error-codes-4).
A Linux provider *load* failure is the one narrow exception, because its cause is actionable and its shape is fixed: when the dynamic loader reports `<soname>: cannot open shared object file`, the adapter admits the soname alone, and only when it matches a `lib*.so[.N...]` shape.
That value becomes the `missingLibrary` field of `provider_unavailable`, the first `GSSAPI_UNAVAILABLE` remedy, and a `gssapi-provider-load-result` trace field; the addon path and every other part of the loader's message stay redacted, and no other platform or message shape produces it.
A minimal ldap-axi-owned socket-gating transport uses the documented `createSecureConnection` hook to send binary SASL BindRequests and decode binary BindResponses before exposing an authenticated protected duplex to `ldapts`.
It accepts either a later inner `secureConnect` event or an already-open verified TLS socket, starts authentication once, and forwards exactly one `secureConnect` only after the protected wrapper has transitioned from `opening` to `open`.
The already-open path is deferred until after the connection factory returns so `ldapts` can subscribe before readiness is emitted.
When the provider completes its context with an empty response token, the next same-mechanism BindRequest omits the optional SASL credentials field rather than encoding a zero-length OCTET STRING.
Active Directory's final BindResponse carries a zero-length `serverSaslCreds`, so only a non-empty token after the completed security-layer negotiation is a protocol violation.
Its BER length decoder accepts non-minimal definite lengths, because RFC 4511 §5.1 requires a definite form and not a minimal one, and Active Directory encodes every LDAPMessage length in four-octet long form including values below 128.
Rejecting a long-form length under 128 stalled the live round-2 BindResponse and is recorded in the Phase 0 live transport report.
It does not call private ldapts methods or copy the ldapts library.

The native provider preserves the existing `wrap()` return type and adds typed wrap and unwrap results containing the protected token plus the actual confidentiality and integrity results.
On Unix those results come from the `conf_state` output from `gss_wrap` and the negotiated `GSS_C_INTEG_FLAG` context capability.
On Windows confidentiality is true only after the requested encrypted `EncryptMessage` operation succeeds against a context whose returned attributes support confidentiality, and integrity reflects `ISC_RET_INTEGRITY`.
The adapter accepts up to 64 KiB of caller-supplied channel-binding application bytes, copies them before asynchronous native work, and supplies the same binding on every context continuation.
Preparation accepts a typed `none`, `integrity`, or `confidentiality` protection requirement.
§10.7's URL scheme, not a flag, selects that requirement.
The legacy no-layer seam remains available only to direct offline compatibility callers.
Integrity and confidentiality requirements add the corresponding Unix GSS or Windows SSPI request flags before the first context token, confidentiality also requires integrity, and context completion rejects any requested capability absent from the provider's returned flags.
Unix constructs a scoped `gss_channel_bindings_struct` for `gss_init_sec_context`.
Windows constructs a native-owned `SEC_CHANNEL_BINDINGS` buffer with checked offsets and lengths for `InitializeSecurityContext`.
Absent input uses the true null/no-bindings path.
Raw tokens, binding bytes, handles, and native error prose never leave the directory boundary.

For live diagnosis, `LDAP_AXI_GSSAPI_TRACE=1` enables a minimal stderr trace with monotonic elapsed time.
The trace records only TLS connection and deadline transitions, inner and wrapper readiness, channel-binding byte counts and authorization state, provider and context status, bind message/result byte counts, native write state, bounded backpressure and byte-count samples, native data lengths, allowlisted transport error categories and codes, RFC 4752 offer and selection byte counts, the rootDSE count and relevant supported SASL mechanism names, pending resolution state, and stable negotiation-failure phases.
The trace is disabled by default, has no timing or behavior effect when disabled, and never records hosts, identities, mechanisms, services, credentials, certificates, tokens, or raw errors.

The RFC 4752 transport seam validates the server offer and selects exactly the layer §10.7's transport requires.
The server must offer the selected layer, the provider must prove the selected outbound and inbound protection state, and a failed proof releases no unwrapped LDAP bytes.
The selected maximum buffer is bounded by the client, server, LDAP-message, and provider limits.
On the sealed plaintext transport every post-bind LDAP write crosses the protected stream in chunks bounded by the negotiated plaintext limit, each framed as a four-octet network-order length followed by one wrapped token.
Raw BER never reaches the native transport after that handoff, and the protected stream exposes neither the native context nor wrap and unwrap operations.
StartTLS completes before the first GSSAPI BindRequest, and explicit simple authentication remains outside the GSSAPI transport.

The Linux adapter passes the Kerberos V5 mechanism OID explicitly for `GSSAPI`, because `GSS_C_NO_OID` leaves mechanism selection to the local GSS-API implementation; Windows passes the SPNEGO mechanism OID for `GSS-SPNEGO`.
The provider requests mutual authentication, sequence protection, and integrity for every new protected GSSAPI exchange, adding confidentiality only when requested.
A stronger typed preparation requirement adds and verifies the corresponding returned capabilities without inferring one capability from another.
The RFC 4752 exchange preserves binary token bytes and limits one exchange to eight continuations, 64 KiB per token, and 256 KiB across all tokens.
The layer-selection token of a protected plan is protected by the provider's integrity-capable operation.
If the server requires a layer that the provider cannot prove, the bind fails without downgrade or fallback.

### 10.7 Two GSSAPI transports, selected by the URL scheme

D1 option C defines the contract: **ldap-axi speaks both GSSAPI transports, the URL
scheme selects which one, and neither falls back to the other.**

| | `ldaps://`, or `ldap://` with `--start-tls` | `ldap://` without `--start-tls` |
| --- | --- | --- |
| Channel | TLS, verified; `--tls-no-verify` is refused | Plaintext TCP, sealed by GSSAPI |
| Channel binding | `tls-server-end-point`, always sent | None; the true no-bindings path |
| SASL security layer | **none** (`0x01`) | **confidentiality** (`0x04`), mandatory |
| Post-bind LDAP | Plain BER over the TLS socket | Every PDU wrapped by the protected stream |
| `--insecure-plaintext` | Not applicable | Not required, because the transport is not plaintext after the bind |

The reasoning is that each transport already carries exactly one confidentiality mechanism, and stacking a
second one is cost without protection.
Under TLS the SASL layer would encrypt bytes that are encrypted already, and Active Directory accepts the
`none` selection from a channel-bound context; on plain 389 there is no other mechanism, so anything weaker
than confidentiality would put directory content on the wire in the clear.

Selection is by scheme alone.
There is no probe, no downgrade, and no second attempt on the other transport after a failure, so one
invocation produces at most one bind (§2.3, §11.6).
`--gssapi-protection` therefore no longer selects the layer: it is accepted only when it names the layer the
scheme already requires, which is `confidentiality` on `ldap://`, and any other value is a
`VALIDATION_ERROR` naming this rule rather than a silently honored or silently ignored request.

The live evidence for both halves is the Phase 0 report cited in §21: the domain controller answered all
three SASL rounds of a channel-bound LDAPS bind and refused an unbound one with `80090346`, and it completed
a GSSAPI bind over plain 389 with a security layer installed.

## 11. Credentials and secrets

### 11.1 Credential-standard profiles and SecretRefs

Configuration follows artium-axi's AXI Credential Standard v2, with the Windows exception in §11.3.
The package ships `axi-credential.schema.json`, the strict schema of one profile, with `bindPassword` marked `x-secret`.
The config shape is `{version:1, defaultProfile, profiles:{name:profile}}`.
Profile names match `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`, and every profile requires a directory URL.
Unknown fields, invalid references, inline secrets, and malformed settings are `CONFIG_INVALID`.
One invocation selects one profile: `--profile`, `LDAP_AXI_PROFILE`, a complete env profile, `defaultProfile`, then the sole file profile.
An explicitly selected or default profile that does not exist is `PROFILE_NOT_FOUND`.
Without a selected env profile, an empty profiles object is `PROFILE_REQUIRED`; several file profiles without a selection are `PROFILE_AMBIGUOUS`.
Without a config or env profile, ambient authentication remains available with a URL flag, and the offline home remains available without a URL.

A file-selected profile ignores env profile fields, except variables named by its SecretRefs or the default password reference when `bindPassword` is omitted.
Non-secret flags override the selected profile, whose values override built-in defaults.
The env profile uses `LDAP_AXI_<SCREAMING_SNAKE_FIELD>` names, including `LDAP_AXI_URL`, `LDAP_AXI_AUTH`, `LDAP_AXI_BIND_DN`, and `LDAP_AXI_BIND_PASSWORD`.
Its endpoint must be supplied by `LDAP_AXI_URL` or `--url`.
Boolean env values accept only `1`, `true`, `0`, or `false`, case-insensitively.
`LDAP_AXI_READ_ONLY` is validated, but v1 remains read-only even when it is false.
`LDAP_AXI_WRITE_LOG` is accepted as host policy; no v1 operation writes, so there is no write journal.

`bindDn` is the non-secret simple-bind identity.
`bindPassword` is exactly `{env:NAME}` or `{file:absolutePath}`, defaulting to `{env:LDAP_AXI_BIND_PASSWORD}` when omitted.
Environment names are validated at config load, not just at resolution.
Windows file references require absolute drive paths and reject UNC and device paths.
Password files are UTF-8 with a leading BOM and trailing whitespace removed.
ldap-axi has no secret storage or `auth login`, so `{stored:true}` is refused.
Only effective `auth: simple` resolves the password; ambient auth never reads a simple-bind password file.
`auth status` reports the selected profile, config path, and password source without emitting the password.

The old top-level config and `credentials.env` formats are never used for authentication.
Legacy config produces `CONFIG_MOVED` with format-conversion help.
When no new config exists, a legacy credentials file is detected by metadata only and produces `CONFIG_MOVED` with SecretRef conversion help.
`LDAP_AXI_CREDENTIALS_FILE` identifies only a legacy location for that check.

When resolving an env profile, `LDAP_AXI_BIND_DN` without `LDAP_AXI_BIND_PASSWORD`, or the reverse, is `CREDENTIAL_INCOMPLETE` at exit 2
naming the missing half, and the credentials file is **not** consulted as a fallback.
That atomicity rule is inherited from `falcon-axi`: a half-configured environment is a mistake to report, not
a state to silently paper over with a different credential source, because the operator would then be
authenticated as somebody they did not intend.

Authentication mode resolves from `--auth`, then the selected profile, defaulting immediately to `auto`.
Valid values are `auto`, `gssapi`, and `simple`.
GSSAPI service resolves from `--gssapi-service`, then the selected profile,
and otherwise derives one service from the URL host without reverse-DNS canonicalization
or a candidate ladder.
An IP-literal URL requires an explicit `--gssapi-service` whenever GSSAPI may be selected.
`auto` attempts exactly one ambient context and terminates with a stable GSSAPI error when the optional provider, runtime, ambient credential, target, or context is unavailable.
It never silently selects a resolved simple credential.
Only explicit `--auth simple` or a selected profile's `auth: simple` selects the password route.

### 11.2 No secret is ever a command-line argument

There is no `--bind-password`, no `--password`, and no `--secret`.
The reference implementation accepts `-bind-password` on argv, which exposes the credential in the process
table to every local user and in shell history; that is the specific failure being designed out.

Enforcement is mechanical, following the sibling pattern: a **flag-registration guard** throws at startup if
any declared flag name matches a secret-shaped pattern (`password`, `passwd`, `secret`, `token`, `credential`,
`key`).
A test asserts that declaring `--bind-password` throws.
LDAP URL userinfo is also rejected, so `--url` cannot become an alternate path for credentials in argv.
This makes the rule impossible to violate accidentally in a later change, rather than a convention a reviewer
must catch.

No Kerberos password, keytab, raw token, cache content, or ticket is accepted on argv.
Ambient Unix cache selection uses the platform's `KRB5CCNAME` behavior, and Windows uses the current logged-in
security context with no supplied password.

### 11.3 File provenance checks, and the Windows gap stated honestly

On POSIX, config and password-reference files must be **regular files, not symlinks, owned by the current user, with no
group or world permission bits**.
A file failing any of those is `CONFIG_INSECURE` and is **never read**, and the message never echoes a
value from it.
The opened descriptor is checked against the original metadata before reading, and POSIX uses `O_NOFOLLOW`.
The config rule is stricter than the credential standard's group-write prohibition, preserving ldap-axi's existing private-config requirement.

**On Windows those checks do not mean what they mean on POSIX, and the design says so rather than copying the
POSIX check and pretending.**
Windows file security is ACL-based; `fs.stat().mode` does not report a meaningful permission set, and a naive
`mode & 0o077` test is either vacuous or wrongly triggered.
Correctly evaluating a Windows ACL from Node requires either a native module (§15.1 forbids it) or shelling
out to `icacls` (§15.1 forbids that too).

So v1's Windows behavior is:

- The regular-file and not-a-symlink checks still apply, because those are meaningful on Windows.
- The permission check is **skipped**.
  When simple authentication reads a password-file SecretRef, `auth status` reports `credentials_file_permissions: unchecked (windows)`.
  Other selections report `not-used`; this field does not report config-file permissions.
- The README states plainly that on Windows the operator owns file access control, and points at the directory
  ACL as the mechanism.

This is an explicit exception to the credential standard's DACL-verification requirement, authorized for this migration because the maintainer-set runtime subprocess and platform-tool ban remains binding.
No Windows DACL guarantee or full Windows hosted-safe conformance is claimed.

Reporting the gap is the honest design.
Silently skipping the check while the documentation claims a `0600` guarantee would be worse than not having
the check, because an operator would believe in a protection that was not there.

### 11.4 Redaction

Each invocation registers every resolved password in raw, JSON-escaped, and URL-encoded forms.
Exact-secret and pattern matches are computed against the original string and merged before replacement, so neither matcher can hide evidence from the other.
Redaction applies to **stdout and stderr**, including debug logging, error messages, and any structure that
reaches a formatter.
LDAP uses no HTTP Basic authentication and mints no access tokens.
Returned payloads additionally redact secret-shaped keys and private-key, JWT, SAS, and AccountKey value patterns.
String values and help text are redacted before TOON encoding, preserving field names and syntax.
Complete attribute values are redacted before truncation, including requested attributes on user and group reads.

Two LDAP-specific additions to the fleet's usual set:

- **A bind DN is not a secret but it is identifying**, so it is printed only by `auth status` and never
  incidentally in an error.
- **`userPassword` and `unicodePwd` are never requested and never emitted**, even though on some directories a
  sufficiently privileged bind can read hashes.
  They and their numeric OID aliases are on a **never-request attribute denylist**.
  Because LDAP provides no "all except password attributes" selector, `entry search` and `entry show` default
  to `objectClass,cn` and reject the `*` and `+` attribute wildcards; callers request any other safe attributes
  by name with `--attributes`.
  A read-only tool that will happily dump password hashes is read-only in the least useful sense, and this
  denylist is the one place where v1 declines to read something it technically could.

### 11.5 Anonymous bind

Some directories permit an anonymous read, and refusing to support that would make v1 useless against them.
`--anonymous` selects anonymous before connection and conflicts with `--auth`, a configured GSSAPI service, and
configured simple credentials, even when ambient authentication would leave the password unresolved.
It is never reached as fallback from either simple or GSSAPI.
`auto` is not a password fallback: it terminates when ambient preparation cannot produce a usable context.
A silent fallback would turn a credential misconfiguration into a quietly different and much smaller result set,
which is the same class of failure as §9.1's silent truncation.

### 11.6 No credential probing

Following from §2.3, these shapes do not exist in v1, and their absence is a rule rather than an omission:

- No `--try-passwords`, password list, or any flag accepting more than one credential.
- No retry after a bind failure, and no fallback across bind mechanisms or DN forms.
- No fallback after the first LDAP BindRequest.
- `auto` never selects simple implicitly, including when ambient credentials are absent or expired.
- Provider absence, no ambient credential, KDC, SPN, runtime, policy, TLS, and server bind failures are terminal.
- A multi-message SASL continuation with one mechanism is one exchange, not a retry.
- No `test-credentials` or `verify-login` command.
  `auth status` performs the same single logical exchange an ordinary command performs, and reports it.
- No loop construct anywhere that could issue a second authentication mechanism for the same invocation.

A tool that binds repeatedly with varying credentials is a password sprayer, and against AD it is also an
account-lockout weapon.
This is stated in the design because the capability is a natural-looking feature request, and the answer needs
to be on record before it is asked.

### 11.7 Provisioning asks for read access only

The documented setup instructs the operator to provide an account with **directory read access only**.
For AD, that is an ordinary unprivileged domain account; being a member of Domain Admins is explicitly
unnecessary and discouraged.
For generic LDAPv3, it is an account or anonymous access with read on the relevant subtree.

ldap-axi cannot verify that the account is read-limited, and it does not claim to: LDAP exposes no scope
enumeration, so a bind account's rights are not introspectable the way an OAuth scope list is.
That limitation is why the enforcement lives in the client (§3.3) rather than in the credential.
The invariant holds even with an account that could write, because ldap-axi cannot construct a write.
That is the strongest form of the guarantee available here, and it is the reason §3.3 is written as
architecture rather than as policy.

## 12. Structured errors

### 12.1 One envelope

Errors go to **stdout**, in TOON, per AXI §6.

```
error: "<what went wrong, in plain language>"
code: <STABLE_CODE>
help[N]: "<actionable next command>","<another>"
```

Exit codes: `0` success including empty results and partial results, `1` error, `2` usage error.
AXI §6's idempotent-mutation no-op rule has no v1 instances, because there are no mutations.

### 12.2 The code table

Codes shared with the sibling CLIs keep their sibling meanings, so an agent that has handled `VALIDATION_ERROR`
or `TLS_UNTRUSTED` from `awx-axi` or `falcon-axi` already knows them.

a bug report is one line long.

### 12.3 How a failure tells an agent what to do next

Each code maps to a fixed remedy shape, so the agent's next move is deterministic:

| Code | The next move it hands the agent |
| --- | --- |
| `AUTH_REQUIRED` | Set a complete simple-bind env profile or select a profile with bindDn and a bindPassword SecretRef |
| `CREDENTIAL_INCOMPLETE` | The missing variable, and set both or unset the pair |
| `AUTH_FAILED` | Verify the bind DN form: AD accepts `user@domain` and a full DN; **never** a suggestion to retry, per §11.6 |
| `ACCOUNT_LOCKED` / `ACCOUNT_DISABLED` / `ACCOUNT_EXPIRED` / `PASSWORD_EXPIRED` | The concrete account state, and that an administrator must resolve it; explicitly that ldap-axi cannot (§1.5) |
| `INSUFFICIENT_ACCESS` | The DN and attributes that were refused, and that read access to that subtree is needed |
| `STRONGER_AUTH_REQUIRED` | Use verified `ldaps://` or `--start-tls`; if TLS is already verified, investigate the server's stronger-authentication policy |
| `NOT_FOUND` | Every path explains that the search base may be absent or hidden by access control and suggests an authenticated bind with read access when using `--anonymous`; identity lookups also explain the required DN shape or suggest a distinguished name (§5.5) |
| `UNSUPPORTED_BY_SERVER` | The detected flavor, what was requested, and the closest supported alternative (§7.2) |
| `SERVER_LIMIT` | Narrow the filter, lower `--max-rows`, or scope the base more tightly; and which limit was hit |
| `TLS_UNTRUSTED` | `--ca-file <pem>` to append a corporate CA, or `NODE_EXTRA_CA_CERTS`; and that Node does not use the system trust store (§10.2) |
| `TLS_REQUIRED` | Use verified `ldaps://` or `--start-tls`; for GSSAPI, drop `--tls-no-verify` or use §10.7's sealed `ldap://` transport |
| `GSSAPI_UNAVAILABLE` | Name the missing provider or runtime and recommend `--auth simple` only as a new invocation |
| `GSSAPI_CREDENTIAL_UNAVAILABLE` | Obtain an ambient credential with the platform's normal sign-in or `kinit`, or explicitly choose simple in a new invocation |
| `GSSAPI_PREPARATION_FAILED` | Confirm an ambient credential exists and is current, name the other possible preparation causes, and never recommend automatic retry or fallback |
| `GSSAPI_NEGOTIATION_FAILED` | Name the selected wire mechanism and security-layer requirement, without printing tokens or native error prose |
| `VALIDATION_ERROR` | The command's valid flags, inlined (AXI §6) |

The `TLS_UNTRUSTED` remedy is worth its own note.
The naive message, "certificate verification failed", sends an agent looking at the server.
The measured fact in §10.2 is that Node's trust store does not include the corporate CA that the operating
system does, so the actionable remedy names the CA mechanisms.
That is AXI §6's translation rule applied to the failure this tool will most often hit inside a corporate
network.

### 12.4 Translation, never passthrough

An LDAP error arrives as a result code plus an optional diagnostic message, and `ldapts` throws a typed error
per code (verified locally: `NoSuchObjectError`, `InvalidCredentialsError`, `InsufficientAccessError`,
`SizeLimitExceededError`, `AdminLimitExceededError`, and about forty more are exported).

The typed errors are convenient and they are **not** the output.
v1 maps the result code and diagnostic to a §12.2 code and composes its own message.
No raw library error string, no `Error` name, no stack trace, and no library or dependency name reaches stdout,
and no suggestion names `ldapts` or any other implementation detail.

The AD diagnostic string is the one place where upstream text is parsed rather than discarded, and only to
extract the `data <hex>` token (§6.6).
The rest of that string, including `DSID` values, is not printed: it is a Microsoft internal identifier that
means nothing to the caller.

Following the `azure-axi` lesson recorded in the fleet, a hand-authored error fixture proves only that the code
agrees with its author.
Every error translation in §12.2 is therefore **provisional** until a real server produces it.
§18.4's local test directory is what removes that provisional status for the generic-LDAPv3 codes; the AD
sub-code table cannot be confirmed without a real domain controller, and §20 records it.

### 12.5 Result codes that are not failures

Stated separately because the naive rule "non-zero result code is an error" is wrong in three places:

- **5 `compareFalse` and 6 `compareTrue`** are Compare's successful answers.
  v1 registers no Compare (§2.1), so this cannot bite today; it is recorded because a future contributor
  adding Compare would otherwise reintroduce it.
- **4, 11, and 3** with entries retained are partial successes at exit 0 (§9.5).
- **10 `referral`** and reference messages are data, not failure (§9.6).

A test asserts each of these, because they are the cases a fixture author gets wrong by symmetry with HTTP
status codes.

### 12.6 Unknown flags fail loud

Per AXI §6, an unrecognized flag is rejected by name before any connection is opened, with the subcommand's
valid flags inlined so the correction takes one turn, at exit 2.
For example, `ldap-axi user list --disable` reports `VALIDATION_ERROR`, names `--disable`, and lists
the accepted flags, including the read filter `--disabled`, without implying a write capability exists.
The accepted flag names come from routing in `src/cli.ts`; the error does not suggest a spelling correction.

Flag sets are per subcommand.
The always-allowed globals are `--help`, `--url`, `--base`, `--start-tls`, `--ca-file`, `--ca-only`,
`--tls-no-verify`, `--tls-max-version`, `--insecure-plaintext`, `--anonymous`, `--config`, `--profile`, `--auth`,
`--gssapi-service`, and `--gssapi-protection`; those pass on every command and are never reported as unknown.

## 13. TOON output

### 13.1 The boundary, and the encoder facts that constrain it

Internal logic is JSON; conversion to TOON happens once, at the output boundary, per AXI §1.

The fleet pins `@toon-format/toon` at **2.3.1**, which implements spec v3.3 while the published spec is newer.
Three behaviors were re-verified locally during this design task, because output shape is observable behavior
and this design must not repeat an assumption:

- **A primitive array of strings encodes inline, comma-joined, and comma-bearing values *are* quoted.**
  `encode({ memberOf: ["CN=Domain Admins,CN=Users,DC=ex,DC=com", "CN=IT Staff,OU=Groups,DC=ex,DC=com"] })`
  produces
  `memberOf[2]: "CN=Domain Admins,CN=Users,DC=ex,DC=com","CN=IT Staff,OU=Groups,DC=ex,DC=com"`.
  This corrects a plausible misreading of the fleet's recorded note: the mangling risk applies to the
  **hand-formatted** help block, which does not pass through `encode()` and therefore gets no automatic
  quoting, not to encoded row data.
  Multi-valued attributes are safe inline, and §13.3's tabular choice is made for readability, not
  correctness.
- **The keyed tabular form is not available at 2.3.1.**
  An object of uniform objects encodes as nested objects.
  So no output shape in this design may depend on it.
- **A multi-line string encodes to one quoted line with escapes.**
  So no long text goes through the encoder; `renderOutput` from `axi-sdk-js` passes a string through
  verbatim, which is the seam for a header plus a raw body.

Following the siblings, the `help[N]:` block, the `count:` line, and truncated values are **hand-formatted**,
with TOON quoting and escaping applied to every element before joining, and row data goes through `encode()`.

Also inherited from the fleet: `axi-sdk-js` 0.1.8 exports only `runAxiCli`, `AxiError`, `exitCodeForError`,
`installSessionStartHooks`, `RESERVED_COMMANDS`, and the update helpers; `renderError` is **not** importable.
So ldap-axi renders by returning a string or object to `runAxiCli` and reports errors by throwing an
`AxiError`, and because §12.2 has many exit-2 codes while `exitCodeForError` maps only the literal
`VALIDATION_ERROR` to exit 2, ldap-axi passes its **own** `formatError` to `runAxiCli` rather than collapsing
its stable codes.

The encoder is pinned **exactly**, not caret-ranged, because its emitted syntax is part of observable output.

### 13.2 Default schemas

Four fields, per AXI §2.
Long-form content lives in the detail view.

```
$ ldap-axi user list --disabled --limit 3
count: 3 of unknown total
users[3]{sam,name,enabled,last_logon}:
  jdoe,"Doe, John",false,"2026-06-14T08:21:00Z"
  asmith,"Smith, Alice",false,never
  svc_backup,"Backup Service",false,unset
help[2]: "Run `ldap-axi user show <sam>` for the full entry","Run `ldap-axi user groups <sam>` for group memberships"
```

`count: 3 of unknown total` is the honest form from §9.3, and the `never` and `unset` values are the §6.3
sentinels rendered rather than converted.

```
$ ldap-axi group members "CN=IT Staff,OU=Groups,DC=ex,DC=com" --nested
count: 12 of unknown total
partial: true
stop_reason: primary_group_members_not_included
transitive: true
method: matching-rule-in-chain
members[12]{sam,name,type}:
  jdoe,"Doe, John",user
  …
```

`transitive` and `method` are not decoration.
§7.2 explains why they are load-bearing: they are the difference between "these are all the members" and
"these are the direct members", and an agent answering a security question needs to know which it received.

`--fields` extends the schema from a per-subcommand allowlist, and `--attributes` requests raw LDAP attributes
directly.
An unknown name in either is a `VALIDATION_ERROR` listing valid names, never a silently dropped column.

### 13.3 Multi-valued attributes and DN lists

LDAP attribute values are always multi-valued in the protocol, so this needs a stated rule rather than an
incidental behavior.

- A single-valued-in-practice attribute renders as a scalar.
- A genuinely multi-valued attribute renders as a TOON array.
- A requested attribute absent from the server response is omitted, including the synthetic zero-value arrays supplied by `ldapts`; a returned empty string remains a value.
- A **DN list** (`member`, `memberOf`, `uniqueMember`) renders as a **tabular block**, one DN per row:

```
memberOf[3]{dn}:
  "CN=Domain Admins,CN=Users,DC=ex,DC=com"
  "CN=IT Staff,OU=Groups,DC=ex,DC=com"
  "CN=VPN Users,OU=Groups,DC=ex,DC=com"
```

Verified locally that the inline form is correctly quoted and therefore also parseable (§13.1), so this is a
readability and row-orientation decision: a DN list is the thing an agent most often iterates, and one DN per
line is greppable and diff-friendly, while a single 300-character inline line is neither.
The decision is recorded as aesthetic rather than dressed up as a correctness fix.

Binary attributes follow §6.2: canonical string plus a `_raw` base64 companion.

### 13.4 Pre-computed aggregates

AXI §4's argument is that the expensive cost is the follow-up call, and LDAP offers less here than an HTTP API
does, which is stated rather than worked around.

- **There is no free total** (§9.3). A total requires walking every page, so `count:` reports `unknown total`
  unless the walk completed. v1 does not issue a second counting search to populate it, because that would
  double the cost of every list for a number the caller may not need.
- **`--count` is offered as an explicit choice**: it walks pages requesting no attributes (`1.1`, the RFC 4511
  no-attributes OID) and returns only the total, which is far cheaper than walking full entries.
- **Group member counts are free when the membership attribute is small**, because it comes back with the
  entry itself, so `group show` reports `member_count` with no extra operation for an ordinary group.
  AD ranges a multi-valued attribute past `MaxValRange` (default 1500) into `member;range=0-1499` chunks; when
  that happens, `group show` (and only `group show`, never `group list`) follows the chunks to completion, up
  to a bounded row cap, because it is reading one entry rather than walking the directory.
  A count capped by that walk reports `member_count_complete: false` alongside `member_count`, so a truncated
  count is never presented as exact.
  On AD, `member_count` counts only the `member` attribute because `primaryGroupID` membership is not stored
  there, so it also reports `member_count_complete: false` and `primary_group_members_not_included`.
  `group list`'s default fields never include `member_count`, precisely because paying that walk cost once per
  row in a directory-wide list is the kind of hidden expense this design avoids elsewhere.
- **Account state uses attributes returned with each user entry**, avoiding separate per-user reads.
  §6.1 owns AD decoding and §7.1 owns generic LDAPv3 state semantics; `src/schema.ts` owns default and selectable fields.

### 13.5 Truncation

Per AXI §3, a long value is truncated with its total size stated:

```
$ ldap-axi entry show "CN=Big Group,OU=Groups,DC=ex,DC=com"
entry:
  dn: "CN=Big Group,OU=Groups,DC=ex,DC=com"
  objectClass[2]: top,group
  member_value_count: 4812
  member_values_truncated: true
  member[50]{dn}:
    "CN=…,OU=Users,DC=ex,DC=com"
    …
```

The limit is 800 characters per scalar field, inside AXI §3's 500-1500 band, and 50 values for a multi-valued
attribute in a detail view.
The `dn` field on user, group, and computer rows remains complete so it can be reused in a show command; redaction still applies.
A field is never omitted entirely.

The 50-value cap needs its own justification, because it is a truncation of a **count** rather than of text: a
`member` attribute on a large AD group can carry thousands of DNs and would otherwise flood a detail view that
an agent asked for something else about.
Every capped multi-valued attribute reports `<attribute>_value_count` and
`<attribute>_values_truncated: true`, so truncation is never invisible.
`group members` is the dedicated bounded route for a group's member list and reports the limitations from
§6.4 and §7.2.

Attribute values are emitted quoted and truncated on a character boundary with no reformatting.
Directory content is **operator-controlled but not necessarily trustworthy** text: a `description` or `cn` can
contain anything a directory administrator typed, including TOON-significant characters, so nothing in the
pipeline reinterprets it.

### 13.6 Definitive empty states

Per AXI §5, the zero is stated with the scope that produced it, so an agent does not re-run to check:

```
$ ldap-axi user list --locked
users: 0 locked accounts under "DC=example,DC=com"
help[1]: "Run `ldap-axi user list --disabled` for disabled accounts instead"
```

Two LDAP-specific empty states get their own wording, because "0 results" and "you cannot see any results" are
different facts:

```
$ ldap-axi computer list --base "DC=example,DC=test"
fallback_filter: (objectClass=device)
computers: "0 entries matched the generic fallback filter \"(objectClass=device)\" under DC=example,DC=test"
note: an entry hidden by access control is indistinguishable from an absent one
tls_verified: true
help[2]: "This server was not detected as Active Directory; computer used a generic device fallback, and machine accounts may not exist in this directory","Run `ldap-axi entry search --filter \"(objectClass=*)\" --scope one` to explore object classes under the selected base"
```

and the access-control case, where an empty result is genuinely ambiguous and the output says so:

```
$ ldap-axi entry search --base "CN=Configuration,DC=ex,DC=com" --filter "(objectClass=*)"
entries: 0 entries matched under "CN=Configuration,DC=ex,DC=com"
note: "an entry hidden by access control is indistinguishable from an absent one; the bind account may lack read access to this subtree"
help[1]: "Run `ldap-axi auth status` to confirm the bound identity"
```

That note follows `awx-axi`'s established practice of saying when an invisible object and a missing object
cannot be told apart.
In LDAP it is the common case rather than an edge case, because access control is applied per entry and per
attribute and a denied read is simply absent from the result rather than reported as denied.

### 14.1 The home view

Running `ldap-axi` with no arguments prints live content, not a manual, per AXI §8, with the identification
AXI §10 requires:

```
$ ldap-axi

description: "Read Active Directory and LDAPv3 directories from the shell (read-only)"

flavor: "Active Directory Domain Services (functional level 7)"

bound_as: "CN=svc-read,OU=Service,DC=example,DC=com"

groups: 212

```

The two counts are the one place the home view spends operations beyond the rootDSE read: two `--count`-style
walks with no attributes (§13.4).
They are included because "how big is this directory" is the orienting fact, and they are cheap in bytes even
when they are several round trips.
If either exceeds a short deadline, the field reports `unknown` rather than delaying the home view, since AXI
§7's token-budget-aware rule applies with more force to a view that may load on every session.

When no credential resolves, the home view prints the identification, the configured URL if any, and the
credential setup help, at exit 0, because "how do I configure this" is the live content in that state.

The shipped v1 home view is the offline part of that shape: the identification, the configured URL when one
resolves, whether simple credentials are configured, and the implemented command list.
Configured simple credentials are labeled `configured for simple auth`, with a reminder that `auto` selects ambient Kerberos/SSPI.
It opens no connection, so it costs no round trip and cannot fail on an unreachable directory, and the two
counts above are deferred with the connected home view to a later stage.
`auth status` is the connected diagnostic, and the home view points at it.

### 14.2 The help hierarchy

Leaf-command help follows AXI §10's target: flags with defaults, required arguments, and two or three examples.
It never dumps the whole CLI.
`entry`, `user`, `group`, `auth`, `profile`, and `config` support group-level `--help`, listing their shipped subcommands and returning exit 0 without reading configuration or contacting the directory.
`entry search` and `auth status` generate their complete flag references from the same accepted flag names used by routing, sharing descriptions with user and group help.
User and group examples demonstrate bounded reads, field selection, identifier or DN lookup, and membership expansion rather than repeating help invocations.
The unknown-flag error inlines the same flag list (§12.6), so a correction is one turn.

### 14.3 Filters are discoverable, because they have to be

An agent that must construct an LDAP filter needs more than a flag list, and this is the LDAP analogue of
`falcon-axi`'s decision to make FQL discoverable.

`ldap-axi entry search --help` identifies RFC 4515 filters, the `&` `|` `!` prefix operators, and the
literal-value escaping rule from §8.2, with an equality-filter example and the presence-filter default.
Help is offline and does not detect server flavor or render AD-specific match rules; §6.5 owns those rules.
RFC 4515 (§21) defines presence, equality, substring, and greater-or-equal filter forms.
Malformed filters produce `VALIDATION_ERROR` before connecting (§8.3).

### 14.4 Authentication selection and migration warning

Every implemented directory command accepts `--auth auto|gssapi|simple`,
`--gssapi-service <service@fqdn>`, and `--gssapi-protection none|confidentiality`.
Per §10.7 the URL scheme, not `--gssapi-protection`, selects the SASL security layer, so that flag is
accepted only when it names the layer the scheme already requires.
`auth status` reports that same selection, and `auth status --offline` reports it without binding.
Offline ambient credentials and provider availability are explicitly unchecked, and `native_provider_installation` names the recorded install outcome separately from `native_provider` runtime availability.
The live GSSAPI report can label the provider available because its one successful bind has loaded it.
Environment fields and their isolation from file-selected profiles follow §11.1.

The immediate default is `auth: auto`.
Phase B loads the optional provider only after the selected transport is ready, supplies TLS channel binding when TLS is present, then prepares one ambient context before the GSSAPI BindRequest.
Provider, runtime, ambient-credential, target, context, TLS, or LDAP failures are terminal and never select a configured password.
Authenticated invocations that require the configured service identity must set `auth: simple` or pass `--auth simple`; anonymous invocations continue to use `--anonymous`.
The `auto` default can change the bound identity for an operator who has both an ambient credential and configured simple-bind credentials, and can therefore change visible directory data even though ldap-axi remains read-only.
Operators that require the configured simple-bind identity must select `simple` explicitly.

## 15. Cross-platform: Linux and Windows

v1 must run on both Linux and Windows.

### 15.1 One optional native provider; no shelling out

Three rules, each with its enforcement:

- **One optional native provider.**
  The package root carries and owns the exact-pinned `kerberos@7.0.0` source, native build, prebuild verification, and package-relative loader.
  It never performs a bare `kerberos` package resolution, so an unmodified registry or hoisted provider cannot masquerade as the patched implementation.
  Install verifies a target artifact's N-API version, patch level, and SHA-256 digest before atomically copying it, then attempts a source build only when a verified artifact is absent or fails capability verification.
  A missing system runtime library does not turn an otherwise verified bundled artifact into a source-build request; the later provider load reports stable `GSSAPI_UNAVAILABLE`, and explicit simple mode remains usable without loading the provider.
  On Linux, `libgssapi_krb5.so.2` must be discoverable by the dynamic loader; when it or any other required library is not, the `GSSAPI_UNAVAILABLE` remedy names that exact soname rather than leaving the operator to guess (§10.6).
  Nix and WSL users may need an environment wrapper or `LD_LIBRARY_PATH`, and ldap-axi does not claim universal zero-config native authentication.
  `docs/support-matrix.md` carries the operator-facing form of this matrix, including the measured hazard that pointing `LD_LIBRARY_PATH` at the whole system library directory breaks a Nix-provided Node before ldap-axi runs at all.
  Linux glibc x64 and Windows x64 are the only admitted native targets.
  Linux musl, Linux arm64, Windows arm64, and macOS are rejected before a source build.
- **No runtime shelling out to `ldapsearch`, `ldp.exe`, `dsquery`, PowerShell, or any platform binary.**
  The tool speaks LDAP itself.
  Enforcement rejects `node:child_process` throughout `src/`; the only exception is the package install and target-native prebuild scripts invoking the pinned `node-gyp` build tool.
- **No POSIX-only assumption in path or config handling.**
  Paths are composed with `node:path`, never by string concatenation with `/`.
  The home and config directories resolve per platform (§15.2).
  Output is LF-terminated on both platforms, because TOON specifies UTF-8 with LF and an agent parsing stdout
  should not receive a different byte stream depending on the operating system.

### 15.2 Config and credential locations

| Platform | Config | Password |
| --- | --- | --- |
| Linux and macOS | absolute `$XDG_CONFIG_HOME/ldap-axi/config.json`, else `~/.config/ldap-axi/config.json` | Env or absolute file SecretRef |
| Windows | `%APPDATA%\ldap-axi\config.json`, ignoring XDG variables | Env or absolute drive-path SecretRef |

Config selection is `--config`, then `LDAP_AXI_CONFIG`, then the platform default.
`LDAP_AXI_CONFIG_FILE` remains a deprecated alias for one minor release, with a stderr notice.
The home directory comes from `os.homedir()`, and config is never discovered from the working directory.
No credentials or state file is written by ldap-axi.
The live-test credential file keeps the sibling convention, `~/.config/ldap-axi/live-smoke.env` (§19).

### 15.3 The `0600` check on Windows

The Windows permission-check exception, its reporting scope, and the operator's access-control responsibility are specified in §11.3.
Copying a POSIX mode test onto Windows and reporting a guarantee that is not enforced would be worse than not
checking.

### 15.4 Node engine, provider exclusions, and the library pin

The provider-foundation PR admits source builds only on Linux glibc x64 and Windows x64.
Its target-bound production scripts create either target's artifact only while running on that target.
The package verifies a bundled target artifact against package-pinned metadata, otherwise fetches only the matching versioned GitHub release binary and verifies it against the digest pinned in the published package before loading it.
Any prebuild fetch, read, schema, digest, or capability verification failure is cleaned up and transitions to exactly one source-build attempt in automatic mode; a missing dynamic runtime library is reported as provider unavailable rather than treated as a capability failure; forced prebuild mode fails closed.
The Linux x64 artifact is built on the pinned Rocky Linux 8.10 baseline and must require no symbol newer than GLIBC_2.28 or GLIBCXX_3.4.25.
It requires glibc 2.28 or newer, a libstdc++ providing GLIBCXX_3.4.25 or newer, compatible Kerberos/GSS runtime libraries, and Node 24.11.0 or newer.
CI behavior-tests it on the minimum Node 24.11.0 runtime in that baseline and load-tests the same artifact on the current Node 24 release.
GitHub-hosted Linux glibc x64 and Windows x64 jobs build and behavior-test both prebuild and forced-source clean consumer paths from the release commit.
The tag workflow validates the build-job checksums, pins both artifact digests into the package manifest, and packs the package before staging all assets on an idempotently updated draft release.
A Windows clean consumer installs that exact packed artifact, fetches the Windows binary privately from the draft release, and verifies its pinned checksum and native capability before publication is permitted.
The consuming job uses a job-scoped `contents: write` token to find the matching tag in the releases list and download the draft asset through its authenticated API URL; a read-only token cannot access the draft.
The support matrix's [release and provenance contract](../support-matrix.md#release-and-provenance) owns the publication order and failure behavior after that consumption succeeds.
Tagged binaries and the package receive GitHub artifact provenance attestations and are attached to the matching release, but the binaries are not Authenticode or platform-code-signed.
Package installation trusts the package-pinned digest and does not independently verify the attestation.
This source tree bundles a Linux glibc x64 N-API 9 artifact of approximately 272 KB; Windows x64 is consumed from its target-native release artifact.
Linux musl, Linux arm64, Windows arm64, and macOS are unsupported.
Every Linux native path, including a verified prebuild, requires compatible system Kerberos/GSS runtime libraries.
The published Linux artifact requires `libgssapi_krb5.so.2` to be discoverable by the system dynamic loader; Nix and WSL users should use an environment wrapper or `LD_LIBRARY_PATH` when their runtime store is not on the loader path.
Linux source builds additionally require Python, the pinned node-gyp dependency, a C++ compiler, and Kerberos/GSS development headers.
Windows source builds require node-gyp, MSVC, and the Windows SDK.
node-gyp can require network access to obtain matching Node headers when its cache is cold.
The optional native build dependency graph is normally installed and costs roughly 10 MB unpacked even for an operator who uses only simple authentication.

**`engines.node` is `>=24.11.0`.**

The floor applies to every supported platform, including offline commands and simple authentication.

**`ldapts` is pinned at exactly `9.0.0`.**

The earlier draft of this design pinned `8.2.0`, for one reason only: `9.0.0` declares `engines.node >= 22`
while the fleet floor was 20.
A 24.11.0 floor removes that reason entirely, so the pin moves up.

The move was verified rather than assumed, because §8.1, §10.3, and §10.4 are all version-specific source
facts and a pin change could silently invalidate them.
The complete published source delta from `8.2.0` to `9.0.0` is **two removals**:

- the `Symbol.asyncDispose ??= Symbol('Symbol.asyncDispose')` polyfill for Node < 22, which is precisely why
  the library's own floor moved to 22 and which a 24.11.0 floor makes dead weight;
- the deprecated `Filter.prototype.escape()` instance method, whose static replacement `Filter.escape()`
  remains.

Nothing else changed: no behavioral change to connection handling, paging, filters, TLS, or errors.
All three traps above were re-checked against `9.0.0` and behave identically; the only edit they required is
the source line number cited in §10.3.

That matters because "use the modular ldapjs rewrite" is the natural answer to ldapjs being archived, and there

### 16.2 `ldapts`, with its surface verified rather than read

Every claim in this subsection was checked by importing the installed package, following the fleet's recorded
lesson that a dependency's real surface must be verified by importing it, not by reading its declarations.

- **Promise-based, TypeScript-first**, bundled types at `./dist/index.d.ts`, ESM and CJS entry points
  (`dist/index.mjs`, `dist/index.cjs`) declared through an `exports` map with a single `"."` entry.
  The entry-point shape is worth noting because the fleet has been bitten by an `exports` map before: a deep
  import path into this package would fail the same way.
- **The complete `Client` prototype surface** is listed in §3.3 item 1, including the runtime-reachable
  `_send`, which is what makes the wrapper design necessary rather than optional.
- **The built-in `SASL_MECHANISMS` list is exactly** `["EXTERNAL","PLAIN","DIGEST-MD5","SCRAM-SHA-1"]`.
  So ldapts's public `bindSASL()` helper does not provide GSSAPI, Kerberos, NTLM, or SPNEGO.
  Phase B uses the separate sealed binary bind transport in §10.6 rather than that helper.
- **Controls**: `PagedResultsControl` (`1.2.840.113556.1.4.319`), `ServerSideSortingRequestControl`
  (`1.2.840.113556.1.4.473`), `PersistentSearchControl`, `EntryChangeNotificationControl`, and a generic
  `Control` accepting any OID. No VLV.
- **`escapeFilter` is a tagged template function** whose plain-function misuse silently returns the first
  character (§8.1).
- **`startTLS` calls its own `exop`** and sets `options.socket` without `servername` (§10.3), and
  `secure = isSecureProtocol || hasTlsOptions` (§10.4).
- **`searchPaginated` yields flattened entries, not `SearchEntry` instances.**
  Each element is `{ dn, ...attributes }`, and its index signature makes `entry.attributes` type-check while
  evaluating to `undefined` at runtime, so every read path destructures `dn` away rather than reaching for an
  `attributes` property.
  Proved live: the rootDSE probe threw on the first real entry it ever saw.
- **Referrals are collected, never chased** (§9.6).
- **`timeout` and `connectTimeout` both default to 0**, meaning no timeout (§9.5).

### 16.3 The rejected options, each with its reason

- **`ldapjs`**: archived, callback and EventEmitter based, no bundled types.
  Its own maintainer's closing recommendation is to write such a gateway in another language.
  Its streaming ergonomics and its richer reconnect and multi-URL failover options are genuinely better than
  `ldapts`'s, which is worth recording as the real cost of this decision; an abandoned dependency in a
  security-adjacent tool is still the larger risk.
- **`@ldapjs/*`**: no client package exists (§16.1), so choosing it means writing an LDAP client.
- **`openldapjs`**: last published 2018, repository gone.
- **`ldap-native`**: 0.1.x, 0 stars, native compilation against `libldap`/`liblber` and Cyrus SASL on POSIX or
  `Wldap32` on Windows, and its own README states that it wraps **synchronous** `libldap` calls behind
  promise-shaped methods and that generic control encoding is partial.
  It is the only candidate offering GSSAPI, which is the one thing that made it worth evaluating, and every
  other property disqualifies it against §15.1.

### 16.4 Recommendation, and the risks it carries

**Use `ldapts`, pinned at `9.0.0`, driven exclusively through `searchPaginated`, behind the sealed read-only
wrapper of §3.3.**

It is the only genuinely maintained, pure-JavaScript, promise-native, TypeScript-first option; the paged
results control is built in; `tlsOptions` is plain `tls.ConnectionOptions`, so §10.2's corporate CA problem is
solvable; and its mutation surface is a short, closed, verified list that §3.3 can seal.

Risks, recorded rather than glossed:

1. **Bus factor.** A small single-maintainer project. Mitigation: it is pure JavaScript with one dependency,
   so it is vendorable if maintenance stops. That is materially better than `ldapjs`'s already-realized
   abandonment.
2. **Node engine floor** (§15.4).
   ldap-axi requires Node >= 24.11.0 on every platform.
3. **Three version-specific traps** (§8.1, §10.3, §10.4) that must be re-verified on any upgrade. Each has a
   test attached for exactly that reason.
4. **GSSAPI provider behavior is offline-provable in Phase B but not live-qualified.**
   The in-repository provider adapter and narrow native patch expose actual confidentiality and integrity results, channel-binding application data, RFC 4752 security-layer negotiation, and post-bind LDAP framing; live ticket acquisition and server interoperability remain outside the required checks.
5. **No idle or backoff reconnect policy**, accepted because v1's model is one connection per invocation
   (§9.5).
6. **`search()` with `paged: true` silently buffers everything**, which is a foot-gun inside the dependency
   rather than in ldap-axi; §9.2 forbids that call and a lint rule can enforce it.

## 17. Configuration and session integration

### 17.1 Configuration holds no secrets

`config.json` at the §15.2 location holds the version 1 profiles envelope specified in §11.1.
The authoritative profile field schema is `axi-credential.schema.json` (§11.1).
No inline secret is accepted, and unknown keys are rejected.
Selection, source isolation, and flag precedence follow §11.1.
The config is held to the same private-file provenance rules as password-reference files (§11.3), including the documented Windows exception.
`config path` reports the chosen path without reading config or secrets.
`profile list` validates config and lists names, endpoints, and auth modes without resolving secrets.

A `flavor` override exists for the case §5.2 admits it cannot handle: a directory that is AD-like but does not
advertise the capability OID, or a generic server that a future ldap-axi misclassifies.
It is an override, not a default, and `server` reports when detection was overridden so a wrong override is
visible rather than mysterious.

### 17.2 Session hook and skill

Per AXI §7, `ldap-axi setup` installs, by explicit opt-in only:

- A **session-start hook** for Claude Code (`~/.claude/settings.json` or project settings), Codex
  (`~/.codex/hooks.json` with `[features].hooks = true`), and a managed OpenCode plugin, selected by `--app`.
  The injected context is the §14.1 home view, which is deliberately small.
- An installable **skill**, generated from the same content the home view prints, so the two cannot drift, with
  a `--check` mode that fails local verification if the committed skill is stale.

The skill omits live state, since a skill is static, and rewrites examples to a form that runs without a global
install.
Both paths are documented in the README as two ways to achieve the same thing, with the hook recommended first.

One ldap-axi-specific caution on the ambient hook: the home view performs a bind and two counting walks
(§14.1).
A hook that loads on every session therefore touches the directory on every session, which is a footprint an
operator should choose deliberately (§3.6).
So `setup` states that plainly, and the hook's home view honors a short deadline and reports `unknown` counts
rather than delaying session start.

## 18. Testing: offline fixtures and a local directory

### 18.1 The seam

There are exactly two implementations of §3.3's `Directory` interface:

- **`LdapDirectory`**, which holds the `ldapts` client and speaks to a real server.
- **`RecordedDirectory`**, which serves synthetic fixtures keyed on the search request without any network
  access.

Separately, the GSSAPI seam supplies an in-memory provider and binary SASL sender to offline tests, while the production adapter is the only code that dynamically loads the package-relative vendored provider; neither is a `Directory` implementation or runtime-selectable directory.

The substitution is **compile-time and test-only**, following `falcon-axi`'s reasoning: a runtime-selectable
implementation, especially one keyed on an environment variable, would be a seam around the very checks §3.3
presents as unbypassable.
Offline tests build against `RecordedDirectory` by module resolution; the shipped binary contains only
`LdapDirectory`; and no flag, environment variable, config key, or exported setter can reach the recorded
implementation in a released build.

Because domain modules are pure functions from arguments to search requests, and from search pages to TOON,
every command is testable end to end with no network and no mocking framework.

`ldapts`'s `createConnection` and `createSecureConnection` options (verified present in 9.0.0) give a second,
lower seam for the few tests that must exercise the real client's own behavior, in particular §10.3's
host identity options and §10.4's implicit-TLS trap, which live below the `Directory` interface and cannot be
reached from `RecordedDirectory`.

### 18.2 Layout

```
test/
  fixtures/
    rootdse/       AD DS, AD LDS, OpenLDAP-shaped, and a minimal LDAPv3 rootDSE
    entries/       user, group, computer, posixAccount, posixGroup, groupOfUniqueNames
    paging/        multi-page cookie walks, empty-cookie termination, rejected cookie
    binary/        objectSid and objectGUID byte vectors with known canonical forms
    errors/        result codes 4, 8, 10, 11, 12, 32, 34, 49 with AD data sub-codes, 50, 51
  offline/         one file per core seam and per domain
  local-directory/ opt-in containerized directory suites (§18.4)
  live/            opt-in read-only smoke suite (§19)
  support/         fixtures.ts, toon.ts, run.ts
```

Each fixture carries a provenance header naming the RFC or Microsoft reference it was authored from, the
retrieval date, and `provenance: synthetic`.

### 18.3 Fixtures are wholly synthetic

Every fixture is authored from the specifications cited in §21.
No captured directory response, scrubbed response, real DN, real SID, real GUID, hostname, username, or
tenant datum is committed in any form.
There is no recorder mode and no capture-to-fixture path, so no test run and no live invocation can persist
directory content.

Two offline tests enforce hygiene: one asserts every fixture carries the provenance header, and one asserts no
fixture matches credential, password, or realistic-directory-data patterns.

The binary fixtures deserve a note, because they are the one place where synthetic data must be exactly right:
an `objectSid` byte vector and its expected `S-1-5-21-…` rendering are authored from the SID structure
specification, so the test proves the decoder against the specification rather than against the decoder's own
output.
A round-trip test that only decoded and re-encoded ldap-axi's own bytes would pass with an endianness bug
intact, which is precisely the §6.2 trap.

### 18.4 The local test directory is the drift check

Synthetic fixtures prove deterministic behavior and cannot prove upstream fidelity: a hand-authored fixture
proves only that the code agrees with its author.
For ldap-axi there is a genuinely better answer than for the HTTP-based siblings, and it should be used: **a
real LDAP server runs locally**.

An optional `npm run test:local-directory` suite runs against a containerized **Samba Active Directory domain
controller** seeded by `scripts/local-directory.sh`, which provisions an ephemeral `LDAP.TEST` domain, a
throwaway administrator credential, a Kerberos client with a real ticket, and the DC's own CA, then runs the
suite through the built CLI and destroys every container.
It is **outside** the default `npm run verify` because it requires a container runtime and Linux, and it is the
drift check for everything the fixtures assert: real BER encoding, real paging, real referrals, real result
codes, real `objectSid`, `objectGUID`, FILETIME and `userAccountControl` decoding, and real `tokenGroups`
membership.
Every Samba case is skipped unless that script sets `LDAP_AXI_LOCAL_DIRECTORY`, so the suite stays inert in every
ordinary check, and `.github/workflows/local-directory.yml` runs it only from a manual workflow dispatch.

The same opt-in command then runs `scripts/local-openldap.mjs`, an OpenLDAP plus MIT KDC mock based on Alpine 3.22.
It seeds synthetic `inetOrgPerson`/`posixAccount` users, a permanent ppolicy lock, `groupOfNames` (including a nested group and an escaped DN), `groupOfUniqueNames` (including an optional UID suffix), and `posixGroup` (including an unresolved uid).
Seeding goes through slapd so the memberof overlay maintains real back-links.
The built CLI checks generic memberships, paging and ppolicy filters with simple bind, then authenticates with an isolated ambient Kerberos ticket over LDAPS, StartTLS, and plain LDAP with the mandatory confidentiality layer.
TLS GSSAPI uses channel binding and no SASL layer, which this server supports even though Samba refuses it.
The new cases are inert unless the runner sets `LDAP_AXI_LOCAL_OPENLDAP=1`.
Both runners use unique `ldap-axi-test-` resource names and destroy their containers and networks on exit.
OpenLDAP additionally destroys its volume and uniquely tagged image.
The mock generates secrets and certificates inside its disposable volume, and its client uses temporary HOME/XDG directories, explicit Kerberos config, keytab and credential-cache paths inside the container.
It never reads or changes the host's Kerberos configuration, ticket cache or DNS configuration.
Startup waits follow service log events rather than retrying directory authentication.
This remains outside `npm run verify`, and no GitHub Actions configuration changes are required.
Qualification status belongs in [the support matrix](../support-matrix.md#what-is-proved-and-what-is-not).

It also answers questions the specification cannot, and §9.4's cross-connection cookie validity is the most
important one.

Three findings came from running it, each unreachable from a self-authored fixture:

- `LdapDirectory.rootDSE()` read an `attributes` property that `searchPaginated` entries do not carry, so every
  real-server connection failed. An offline regression now serves one BER `searchResEntry` to pin the fix.
- A domain-root search returns subordinate references for the configuration and DNS partitions, so §9.6 marks
  ordinary AD reads partial while §5.5 rule 4 resolves an identifier through them. The suite pins both: the
  `user list` `stop_reason: referral` and a `user show` identifier that resolves at the domain root.
- TLS SASL-layer restrictions informed §10.7's transport selection; §20 records the decision.

What it **cannot** cover is stated plainly: Samba is not Windows, so Windows SSPI behavior, the Windows bind
sub-error table, and Windows-specific schema remain fixture-only.
A production domain remains the only proof for those.

### 18.5 The tests that carry the design

The highest-value offline tests are the ones covering behavior a naive client gets quietly wrong:

- **Registry and allowlist integrity** (§3.3): exactly the §2.1 operations plus `whoami`; every effect within
  the three-member union; every entry with complete evidence; the extended-OID allowlist exactly the two OIDs
  in §3.4; the control allowlist exactly §3.5's one control; and attempted mutation of every frozen descriptor
  leaving all canonical values unchanged.
- **The sealed client exposes no mutation path**: the exported surface is asserted to be exactly
  `openDirectory` plus the `Directory` methods; a test asserts no exported value carries an `add`, `modify`,
  `modifyDN`, `del`, `exop`, or `_send` property, which is the mechanical form of §3.3 item 1.
- **Architecture boundary**: lint plus an independent source and import-graph scan allow `ldapts`, `node:net`,
  `node:tls`, and `node:dns` only in the sealed client file, and reject `node:child_process` throughout runtime
  source; only the native package install and target-native prebuild scripts may invoke pinned `node-gyp`.
- **Denied extended OID**: an attempt to issue RFC 3062 Password Modify fails with `READ_ONLY_VIOLATION`
  before any bytes are sent, and the StartTLS OID succeeds, proving the allowlist is a filter rather than a
  ban (§3.4).
- **Filter escaping** (§8): `filterValue` produces `\2a` for `*`, `\28`/`\29` for parentheses, `\5c` for
  backslash, and `\00` for NUL, asserted against the byte table; a wildcard flag splits, escapes segments, and
  rejoins with an unescaped `*`; a DN with a leading `#`, a leading space, and a trailing space is escaped;
  and a crafted `--filter` combined with a convenience flag produces a parsed conjunction whose structure the
  crafted value cannot alter.
- **Paging is unconditional**: no code path issues a search without the paged control, and no code path calls
  `search()` rather than `searchPaginated()`.
- **In-process paging semantics**: a three-page fixture walk terminates after the final page; the default
  terminal one-page reads report complete totals or definitive empty states, continuations report `incomplete: page_boundary`; and `--all` requires a positive `--max-rows` so output
  remains bounded.
- **Partial results and stop reasons** (§9.3, §9.5): result code 4 with entries retained yields exit 0 with
  `partial: true` and `stop_reason: server_size_limit`; the same code with nothing retained yields
  `SERVER_LIMIT` at exit 1; a spent row budget yields `stop_reason: max_rows`; and a complete read emits no
  partial marker.
- **`count:` never fabricates a total**: an incomplete walk renders `of unknown total`.
- **Flavor detection** (§5.2): the AD capability OID selects AD; the AD LDS OID selects AD LDS and resolves the
  base from `namingContexts` rather than `defaultNamingContext`; a rootDSE with neither and no `vendorName`
  reports `ldapv3` with `vendor: unknown` and fabricates nothing; and several naming contexts with no default
  yield `VALIDATION_ERROR` listing them.
- **AD decoding** (§6): `userAccountControl` decodes to the §6.1 flag names; `locked_out` and
  `password_expired` come from `msDS-User-Account-Control-Computed` and **not** from the raw bitfield;
  `objectSid` and `objectGUID` decode to canonical strings from specification-authored byte vectors, with the
  GUID's mixed-endian field order asserted explicitly; FILETIME `0` renders `unset`, `9223372036854775807`
  renders `never`, and an ordinary value renders ISO 8601; and `lastLogonTimestamp` carries
  `last_logon_precision: approximate`.
- **Identifier resolution and continuation references** (§5.5): a subtree search whose pages carry AD's
  domain-root references still resolves a unique identifier, and paging continues past a reference; two
  matches alongside a reference remain `VALIDATION_ERROR`; zero matches alongside references is `NOT_FOUND`
  whose help names each distinct unsearched subtree once; and a terminal `stop_reason: referral` or a server
  limit is still `SERVER_LIMIT`.
- **Group semantics** (§7.2): a `posixGroup` reports `member_form: uid` and fabricates no DNs; a directory
  merges `memberOf` with reverse searches across the generic group shapes and reports the composite method, or `method: reverse-search` without `memberOf`, with
  `transitive: false`; `--nested` on a non-AD flavor yields `UNSUPPORTED_BY_SERVER` rather than being ignored;
  and an AD `memberOf` fallback resolves `primaryGroupID` and reports the composite method.
- **Error translation** (§12): each fixture result code maps to its §12.2 code; AD sub-codes `52e`, `532`,
  `533`, `701`, `773`, and `775` map to their distinct codes; an unrecognized sub-code degrades to
  `AUTH_FAILED` reporting the raw token; codes 5 and 6 are not treated as failures; and no raw library error
  string, error class name, stack trace, or dependency name appears on stdout.
- **No bind retry** (§2.3, §11.6): a failed bind fixture produces exactly one bind attempt, and `autoRebind`
  is asserted off in the constructed client options.
- **Phase B provider and SASL seam** (§2.3, §10.6, §11): table-driven tests assert the patched in-repository provider package shape, mode/source precedence,
  IP-literal service requirements, atomic credentials, anonymous conflicts, zero transport calls during selection,
  terminal ambient-preparation failures, immutable plans, patched-provider base64 conversion, actual confidentiality
  reporting, channel-binding validation and continuation preservation, platform-specific mechanism selection, result-code
  14 continuation, byte-preserving tokens, mechanism-switch rejection, round and token-size caps, scheme-derived layer
  selection, protected-frame bounds, final no-layer compatibility, and no post-bind fallback.
  A mock server encoding AD-style four-octet lengths for both sub-128 and super-128 content proves the BER decoder accepts non-minimal definite lengths, an empty final `serverSaslCreds` completes an exchange while a populated one fails it, and a mock rootDSE entry reaching flavor detection proves the flattened-entry contract in §16.2.
  §10.7's two transports each carry a regression: a verified-LDAPS bind selects the no-layer RFC 4752 selection and
  then reads plain BER over TLS, while a sealed `ldap://` bind selects confidentiality, frames every post-bind PDU,
  and lets no raw BER reach the socket; a requested layer that disagrees with the scheme is a `VALIDATION_ERROR`, and
  neither transport retries on the other.
  A sealed verified-LDAPS regression covers approximately 8 KiB binary tokens, fragmented server responses, paused
  and resumed stream backpressure, AD-shaped result-code 14 continuations, empty-token credential omission, and
  rootDSE handoff only after final bind success.
  Deterministic readiness cases cover delayed and already-open TLS sockets, duplicate inner events, the wrapper's
  `opening`-to-`open` transition, one asynchronous forwarded `secureConnect`, and an ldapts-style subscriber reaching
  the first bind write.
  A competing `ldapts` data handler receives no handshake bytes before handoff and receives post-handoff data, while
  a stalled exchange proves the shared deadline closes the transport with a stable redacted error.
  A Linux dynamic-loader failure naming a missing shared library reports that exact soname as `missingLibrary` and as
  the first `GSSAPI_UNAVAILABLE` remedy, while the same failure on Windows, a non-soname token, and an unrelated
  loader message all report plain provider unavailability with the addon path and native prose still redacted
  (§10.6).
- **TLS construction** (§10.3, §10.4): the StartTLS path passes the URL host, with SNI only for DNS names; `--tls-max-version 1.2`
  becomes `maxVersion: "TLSv1.2"` without changing the omitted default; TLS options are passed to the
  constructor only for `ldaps://` and to `startTLS()` otherwise; `--ca-file` produces a CA list containing
  both the platform roots and the added PEM, while `--ca-only` produces only the added PEM; and
  `--tls-no-verify` emits `tls_verified: false` in the data and a warning on stderr.
- **Credential handling** (§11): declaring `--bind-password` throws at registration; either half of the
  environment pair alone yields `CREDENTIAL_INCOMPLETE` without falling back; a config or SecretRef
  file that is a symlink, non-regular, or group- or world-readable is rejected unread on POSIX; the Windows
  path skips the permission check and reports it as unchecked; a denylisted attribute in `--attributes` is
  refused; and a fixture containing a password value is asserted absent from both streams.
  The isolated HOME/XDG CLI regressions in `test/offline/credentials.test.ts` pin standard profile selection, source isolation, env and file SecretRefs, load-time validation, migration failures, and offline provenance.
  Ambient auth opens no simple-bind secret file.
- **TOON conformance** (§13): every stdout fixture parses; comma-bearing DN values stay quoted in both inline
  and tabular forms; hand-formatted help elements retain their declared count and escaping; and a directory
  value containing TOON-significant characters round-trips without reinterpretation.
- **Unknown flags** (§12.6): rejected by name before any connection, with the subcommand's valid flags
  inlined.
- **A served rootDSE entry** (§5.1): one BER `searchResEntry` written to the real client proves that
  `LdapDirectory.rootDSE()` reads the plain `{ dn, ...attributes }` entry ldapts yields, which
  `RecordedDirectory` cannot prove because it replaces that method.
- **Vendored provider provenance** (§10.6): lint rejects a `vendor/kerberos/UPSTREAM.md` whose recorded
  upstream version, release tag, repository, or npm tarball integrity has drifted from the vendored manifest.
- **Skill drift** (§17.2): both committed generated skills match `createSkillMarkdown()`.
- **Authentication reporting and the home view** (§11, §14.1): `auth status --offline` reports the
  scheme-selected mechanism, SASL security layer, and channel binding without opening a connection; the live
  form resolves the identity through Who Am I only when the server advertises it and otherwise reports the
  configured bind DN as unresolved; a simple-bind plan never renders its password; the recorded native
  installation status is read from the status file, with missing and malformed files reported rather than
  guessed; and the home view lists the implemented commands without connecting.
- **The live smoke script** (§19.5): it refuses to run without `LDAP_AXI_LIVE=1` and without a URL, and its
  evidence file records step names, exit codes, TOON key shapes, error codes, and trace events, with no
  directory value and no endpoint in the file.

## 19. Safe live-test boundaries

This section is a hard rule of the test design, not a recommendation.

### 19.1 What may ever run against a real directory

Only `test/live/`, only when `LDAP_AXI_LIVE=1` is set explicitly, and only the operations in §2.1.

**The live suite may never issue a mutating operation.**
Under §3.3 it structurally cannot: the `Directory` interface exposes three reads and no mutation path exists.
The suite adds a second assertion anyway, because defence in depth is cheap here: its harness records every
operation id and every extended OID issued during the run and fails if either set exceeds §2.1 and §3.4.
The sealed registry, the source-level import boundary, and the harness recorder are three separate controls,
so one forgotten call site does not bypass all three.

### 19.2 Credentials for live tests

The live suite requires an account with **read access only** (§11.7), sourced from
`~/.config/ldap-axi/live-smoke.env` at mode `0600`, following the sibling convention.
Operators supply a real AD endpoint and read-only credentials separately; **v1 does not block on running
this suite**, and this document does not claim it has been run.

The credential is never written anywhere, never printed, never included in a fixture, never logged, and never
in a failure message.
The live harness retains responses only in memory for shape validation and has no persistence interface.

One live-suite rule is specific to LDAP and follows from §2.3: the suite performs **one bind**, and a bind
failure is a terminal suite failure rather than something to retry with a different DN form.
A test suite that retried binds against a real domain controller could lock out the account it was given.

### 19.3 What the live suite asserts

**Shape, not content.**
The rootDSE returns the attributes §5.1 requires; flavor detection resolves to a definite flavor; a paged
search returns at least one page and terminates on an empty cookie; a multi-page walk produces a
continuation; and on AD, a `userAccountControl` value decodes and an `objectGUID` renders as a canonical GUID.

The harness asserts schema and shape in memory, never a specific DN, username, SID, or group, so the suite
stays valid as the directory changes and no directory detail is baked into the repository.

Preconditions are explicit: at least one user entry, at least one group entry, and enough entries in one
container to produce a continuation.
When a precondition is absent, the affected assertion is reported `SKIPPED` and the suite result is
**validation incomplete**, never a pass.
The suite does not provoke error responses, so §12.4's error translations remain provisional.

### 19.4 Local required checks and native artifact automation

The single local entry point is `npm run verify`: typecheck, architecture lint, build, and the implemented offline test set.
Three workflows exist, and no other.
`.github/workflows/native-prebuilds.yml` on pull requests and `main` builds Linux glibc x64 on Rocky Linux 8.10, enforces the GLIBC_2.28 and GLIBCXX_3.4.25 symbol ceilings, load-tests that artifact on minimum and current Node 24 runtimes, and behavior-tests Linux and Windows clean consumer paths; the Windows job runs the whole `npm run verify` gate on its native runner rather than the packaged-consumer test alone.
On a version tag it validates both target-native build outputs, pins their digests in the package manifest, packs and publishes with npm provenance, attests the binaries and package, and attaches the matching assets to the release.
`.github/workflows/local-directory.yml` runs §18.4's containerized suites only from a manual workflow dispatch, never on a pull request, push, or schedule.
For `.github/workflows/release-please.yml`, the [support matrix](../support-matrix.md#release-and-provenance) owns automation status and [CONTRIBUTING.md](../../CONTRIBUTING.md#release-changes) owns contributor and maintainer procedures.

- **The live suite is outside `npm run verify`** and never runs automatically: not on a branch, not on `main`, not on a schedule, not on a repository event.
- **The local-directory suites are also outside `npm run verify`**; §18.4 owns their runtime requirements and opt-in environment guards.
- **No directory credential is stored in any automated service**, and no workflow has a live-directory credential or test step; the local-directory domain and its administrator credential are synthetic and are destroyed with their containers.
- **No fixture recorder exists**, so no check and no live invocation can persist directory content.
- Additional workflows require explicit project approval.

### 19.5 The live smoke script

`npm run smoke:live -- --url ldaps://server:636` (`scripts/live-smoke.mjs`) is the manual live check an
operator runs against an explicitly selected directory with read-only credentials.
It runs only with `LDAP_AXI_LIVE=1`, refuses to start without a URL, and issues one fixed read-only sequence
through the ordinary CLI entry point: the home view, `auth status --offline`, `auth status`, a base-scope
rootDSE read, `user list --limit 1`, and `group list --limit 1`.
One invocation is one bind (§11.6), and every argument the operator adds is forwarded verbatim to each
connecting step (the non-connecting home view runs with no arguments), so the sequence is exercised under the
operator's own transport, CA, and authentication settings.

It enables §10.6's GSSAPI trace and writes a **redacted evidence file**, by default under the temporary
directory and never inside this repository.
The evidence records the step name, its argument vector without the operator's own arguments, the exit code,
the elapsed time, the TOON **key names and element counts** of the output, the error code when a step fails,
the fixed stderr warnings, and the trace events.
It never records a directory value, a DN, the endpoint, or any credential, so an evidence file can be attached
to a report without §18.3's prohibition being violated.

## 20. Open questions

The following architectural decisions are fixed for v1:

1. `auto` is the immediate default.
2. Password means the existing LDAP simple bind and is selected only before any LDAP BindRequest.
3. GSSAPI speaks both transports, selected by the URL scheme with no fallback (D1 option C, answered 2026-09-17): verified LDAPS or StartTLS with channel binding and no SASL security layer, or sealed `ldap://` with a mandatory confidentiality layer (§10.7).
4. Windows may accept the operating system's Negotiate choice within one selected GSS-SPNEGO exchange.
5. Linux musl, Linux arm64, Windows arm64, and macOS are unsupported provider targets.
6. The package root owns the exact-pinned `kerberos@7.0.0` source, package-relative loader, target-native prebuild production, verified release retrieval, and source fallback; it never resolves a registry or hoisted provider.
7. Linux glibc x64 and Windows x64 prebuild and forced-source consumption are behavior-tested on native GitHub-hosted runners, with tagged artifacts attested and attached to the matching release.
8. The provider and transport seam reports actual GSS confidentiality and integrity, consumes caller-supplied channel-binding application data, negotiates the required security layer, and frames post-bind LDAP PDUs.

The immediate-auto migration warning is user-visible: operators that require the configured service identity must
set `auth: simple` before upgrade or invoke `--auth simple`.

### 20.2 Recorded rather than answered

Recorded rather than answered, because a stated unknown is worth more than a confident guess.

1. **Future resumable cursors** (§9.4).
   v1 deliberately does not expose paging cookies because its maintained client has no supported public
   request/response cookie API.
   Revisit only if a maintained client gains that surface, preserving context binding and rejecting stale
   cookies without restart.
2. **The AD bind sub-error table** (§6.6).
   High-confidence operational fact from secondary sources, with only the mapping mechanism documented by
   Microsoft.
   Needs confirmation against a real domain controller, and until then an unrecognized sub-code must degrade
   to `AUTH_FAILED`.
3. **StartTLS hostname verification** (§10.3).
   Source reading establishes that `ldapts` supplies the connected socket without a host identity; it does not establish the live certificate-verification behavior of §10.3's options.
   Needs a live StartTLS endpoint, ideally one with a corporate-issued certificate.
4. **Whether `tokenGroups` is reliably readable by an unprivileged read account** (§6.4).
   It is a constructed attribute on a base-scope read, and whether an ordinary read account can retrieve it
   for another principal was not confirmed.
   If it cannot, `user groups` falls back to `memberOf` plus `primaryGroupID` more often than this design
   assumes, and the default should be reconsidered.
5. **Multi-domain forest membership** (§6.4).
   `memberOf` does not reliably cross domains, and Global Catalog search is deferred (§1.3).
   So `user groups` in a multi-domain forest may under-report, and the honest interim behavior may need to be
   an explicit warning field rather than silence.
6. **Whether AD's `MaxPageSize` is readable** from `supportedLDAPPolicies` on the rootDSE, or whether it
   requires reading the policy object under the configuration naming context.
   §9.2 currently defaults to 1000 on AD rather than reading the server's actual value.
7. **Whether a Samba AD domain controller container is a sufficient AD test double** (§18.4) for the flavor
   path, the decoders, and the matching rules.
   Partly answered: §18.4's suite proves flavor detection, paging, referrals, the binary and timestamp
   decoders, and `tokenGroups` against a real Samba DC. Windows SSPI and the Windows bind sub-error table
   stay open.
8. **A negotiated SASL security layer cannot coexist with TLS on a real directory** (§10.6).
   Measured against Samba 4.19.5: `source4/ldap_server/ldap_bind.c` refuses any SASL bind that negotiated
   sign or seal on a TLS connection unconditionally, with no server-side option, and Windows Active Directory
   applies the same rule.
   This question is now answered by D1 option C (§10.7, locked decision 3, answered 2026-09-17): the TLS
   transport negotiates **no** SASL security layer, and confidentiality moves to the sealed `ldap://`
   transport.
9. **Subordinate referrals make ordinary AD reads partial** (§9.6, §5.5).
   A domain-root search returns continuation references for the configuration and DNS partitions, which is
   normal Active Directory behavior rather than a Samba artifact.
   v1 therefore reports `stop_reason: referral` for a plain `user list`.
   For identifier resolution, a continuation reference
   is reported without spoiling uniqueness, so `user show` and `group show` resolve an identifier at a domain
   root instead of refusing the search as incomplete (§5.5 rule 4).
   The list commands' `stop_reason: referral` is unchanged.

### Live directory observation

- **Phase 0 live transport discovery**, read-only scout run of 2026-09-17 against a production Active Directory
  domain controller, from this repository's `main` at `f32eaf8`.
  Full evidence, including the traced runs, the reference-client controls, and a hex capture of all three SASL
rounds, is in the project's private operations record, outside this repository.
  It is the only live-directory evidence this document cites, and it supersedes guesswork in four places:

  - **The domain controller accepts the channel-bound GSSAPI bind ldap-axi sends over verified LDAPS.**
    All three rounds are answered; round 3 returns `success`, and round 2 carries an RFC 4752 offer of all
    three layers with a 10485760-byte maximum buffer.
    The earlier assumption that AD would refuse a SASL security layer on an already TLS-protected connection is
    not what this domain controller did.
  - **That domain controller enforces LDAP channel binding on LDAPS.**
    A reference client that sends no channel-binding token fails with `80090346` at every SSF setting over
    `ldaps://`, while the same client succeeds over `ldap://` with a security layer.
    ldap-axi's `tls-server-end-point` binding (§10.6) is therefore load-bearing rather than defensive.
  - **Active Directory encodes every LDAPMessage length in 4-byte long form, including values below 128**
    (`30 84 00 00 00 32` for a 50-byte content).
    RFC 4511 §5.1 requires definite-form lengths but does not require minimal encoding, and `ldapts`'s own
    decoder accepts this form.
    ldap-axi's bounded SASL wire decoder rejected it and failed at round 2; that is a client defect to correct,
    not an AD behavior to design around, and its correction is separate implementation work.
  - **Two environment facts, neither a product defect.**
    For roughly forty minutes the domain controller answered no default TLS 1.3 ClientHello carrying the
    hybrid X25519MLKEM768 key share, and no approximately 8 KB bind, from any client, over either port; the
    window ended on its own and `--tls-max-version 1.2` was the reliable path throughout.
    Its LDAPS chain also needed its own root and issuing CA, fetched from the certificate AIA URLs; an
    unrelated corporate root does not verify it, which is §10.2's CA trap observed in production.

  The prior 30-second `GSSAPI_NEGOTIATION_FAILED` deadline recorded before this run was the TLS window above,
  not the SASL exchange.

### Where the siblings' assumptions do not transfer to LDAP

- **There is no HTTP verb to key on.**
  `awx-axi` enforces read-only by rejecting non-GET at its transport seam.
  LDAP has operations, not verbs, and one of them (Extended) is safe or unsafe depending on an OID, so §3.4
  replaces the verb check with an OID allowlist.
- **There is no scope string to cite.**
  `falcon-axi` admits an endpoint only with documentation proving its scope is a read permission.
  LDAP has no scope enumeration and a bind account's rights are not introspectable, so §2.2 substitutes a
  semantic classification with an RFC citation, and §11.7 states plainly that the credential cannot be
  verified as read-limited.
- **There is no free total.**
  Both siblings read a `total` from a pagination envelope.
  LDAP has none, so §9.3 reports `unknown total` rather than fabricating one, and §13.4 makes counting an
  explicit opt-in.
- **Authentication is not a separate endpoint.**
  `falcon-axi` mints an OAuth token against a distinct URL.
  LDAP's Bind is an operation on the same connection with server-side side effects, which is why §2.3 gives it
  its own classification and §11.6 forbids credential probing.
- **The transport can be plaintext.**
  Both siblings speak HTTPS to a known cloud origin.
  LDAP defaults to an unencrypted port and carries authentication on the same connection, so §10 is a
  larger section than either sibling needs.
  Plaintext requires an explicit flag, while a GSSAPI plan selects its transport by URL scheme and seals a plain `ldap://` connection with a mandatory confidentiality layer instead (§10.7).
